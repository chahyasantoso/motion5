# ADR-090: Disposal is one pass, because teardown is a phase

**Status:** Accepted, 2026-09-16

**Context.** [Issue #408](https://github.com/chahyasantoso/motion5/issues/408), found by the quality pass over [#405](https://github.com/chahyasantoso/motion5/pull/405). ADR-083 made the lifecycle one value and said `disposed` is terminal and carries nothing, which retired two hand-written clears. It did not say what a runtime is while it is being retired, and `dispose` needs an answer to that rather than to the question it was asking.

`dispose` guarded on `isDisposed`, then called `#releaseBooking`, which calls `Cancel.cancel`, which is the host's code, and only then set the phase terminal. ADR-084 put the release first deliberately: a retired runtime should not leave the scheduler holding a job it will only refuse. So there is a window in which host code runs on a runtime whose phase still says idle, and a `cancel` that disposes the runtime again re-entered a body that had not recorded that it was running.

The second pass through was not harmless. `#releaseBooking` is safe twice, because it clears `#drainHandle` before touching the port. `unsubscribe` and `PatchRegistry.dispose` are not covered by anything: the shipped manual clock deletes from a `Set` and tolerates a second release, and the `Clock` port contract says only that `subscribe` answers a function. A host that counts its own subscriptions, or that throws on an unknown one, was reachable from a legal `cancel`.

**Decision one. `disposing` is a member of the lifecycle union, and it carries the booking.** The union already answers questions of this shape, so a fourth phase is the same answer ADR-083 gave rather than a flag beside the value it made one. It carries `DrainBooking` because the booking is released _after_ this transition, not before it, so a `disposing` phase that could not hold one would be a phase the program cannot be in at the moment it is in it.

A boolean `#disposing` field beside `#phase` is refused, and refused by name: it is the third boolean ADR-083 deleted, arriving back under a new spelling, and it would make two values able to disagree about one lifecycle.

**Decision two. `dispose` asks whether teardown has begun, and `#report` asks whether it finished.** `isRetiring` answers the first and `isDisposed` still answers the second, and keeping them apart is what preserves ADR-088's decision six exactly as it was decided. A runtime discovering that its port refuses to cancel is still the object that knows that, and withholding it would silence the last thing an ordinary disposal has to say. The existing case that pins that report stays green, which is the check on this decision rather than a happy accident.

**Decision three. Every transition treats retiring as terminal, and `unbookDrain` lowers in place.** `beginFlush`, `endFlush` and `bookingDrain` answer for a retiring runtime the way they answer for a retired one, so a reentrant publication or a drain arriving mid-teardown cannot walk it back to a live phase. `unbookDrain` is the exception that proves the rule: it is the transition `dispose` itself runs, so it lowers the booking and leaves the runtime retiring rather than resolving it to idle.

**Decision four. A public verb is refused during teardown.** `#assertLive` reads `isRetiring`, so a `flush` from inside a host `cancel` cannot publish over a registry the next statements dispose, and cannot book work onto a runtime that is going away. The message does not move, because a runtime being retired is one a caller may no longer use and the existing `/disposed/` assertions are about exactly that. `#drainScheduled`, `#onTick` and `#flushTick` read `isRetiring` for the same reason: a tick can still arrive during teardown, since `unsubscribe` runs after the port is touched.

**Consequences.** The reachable state space grows from five phases to seven, and the state-space case says seven rather than five: the two new ones are `disposing/unbooked` and `disposing/booked`, both reachable and both closed under every transition. No public export, diagnostic id or rule id moves, and `retiring` and `isRetiring` are internal because `GraphRuntime` is not exported from `packages/core/src/index.ts`. `graph-runtime.ts` grows by under a kilobyte and stays under the 30,000-byte sister-document trigger, so this slice owes no `graph-runtime.md`.

One consequence is worth stating rather than discovering. Ordinary disposal is unchanged in every observable way: the phase passes through `disposing` within one synchronous call and no caller can hold a reference to a runtime in that phase except from inside the host callback that made it. The only behaviour that moves is the behaviour of that callback, and it moves from repeating teardown to being refused.

**Alternatives refused.** A `#disposing` boolean beside the phase: refused above. Setting the phase terminal before releasing the booking: refused because ADR-084 chose that order for a reason and it would stop reporting the port that refuses to cancel, which is an existing pinned behaviour rather than an incidental one. Making `unsubscribe` and `PatchRegistry.dispose` individually idempotent: refused as one guard per teardown step, which is the ADR-076 defect, and it would leave the reentrancy itself legal so a later step could reintroduce the cost. Refusing a `dispose` from inside `cancel` by throwing: refused, because disposing twice is a reasonable thing for host code to do and the second call has nothing to complain about; it is answered rather than punished.
