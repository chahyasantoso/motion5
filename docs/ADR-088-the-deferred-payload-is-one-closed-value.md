# ADR-088: The deferred payload is one closed value, and a host cannot reroute a runtime failure

**Status:** Accepted, 2026-09-16

**Context.** Five findings from the second quality pass over the runtime publication seam, read at `ab9d3df56c60570c6629f60d6a4bc08360171327`: [#392](https://github.com/chahyasantoso/motion5/issues/392), [#393](https://github.com/chahyasantoso/motion5/issues/393), [#396](https://github.com/chahyasantoso/motion5/issues/396), [#400](https://github.com/chahyasantoso/motion5/issues/400) and [#401](https://github.com/chahyasantoso/motion5/issues/401). Four of them are one shape: a value that is nearly a discriminated union, with a question answered beside it rather than by it. ADR-083 made the lifecycle and the snapshot memo one value each and left the deferred payload an interface with two fields, and ADR-084 put the frame inside that interface without revisiting what liveness means. The fifth, #400, is the same defect one layer out: an act with five callers and no owner.

**Decision one. `PendingPublication` is a closed branded union rather than an interface with two fields.** Nothing pending is a variant, not an empty instance of the other one. That is what answers [#396](https://github.com/chahyasantoso/motion5/issues/396) structurally: `NOTHING_PENDING` used to cast a live `Set` through `ReadonlySet`, and because the constant is shared by every runtime in the process, one caller reaching that object and mutating it corrupted all of them. Freezing the set or copying it on access both keep the collection and price the mistake; the variant has no collection in it, so there is nothing to hand out and nothing to freeze. The cast is deleted rather than made safe. `deferredSeeds` is the one reader of a deferral's own set and it answers a copy, so no set leaves the module by any path.

The union is branded exactly as the other two are, for the reason [#387](https://github.com/chahyasantoso/motion5/issues/387) gave: a variant declaring only its discriminant is not closed, because TypeScript's excess-property check reads a fresh object literal and not a value arriving through a variable, so a payload stating a frame beside no deferral was assignable through one intermediate `const`.

**Decision two. A deferral is pending exactly when it exists, and a frame is work by itself.** [#392](https://github.com/chahyasantoso/motion5/issues/392) is that `isPending` read the seed count, so a reentrant `flushAtTick([], tick)` stored a frame, booked a drain, answered a deferred batch, and then the drain returned immediately: the job was spent on nothing and the frame stayed stranded until some later publication cleared the payload. The issue offers two answers and this tier had already chosen one in prose: `flush`'s own contract says an empty seed list is not a cheap flush, that it derives the snapshot, moves the sequence and notifies every batch subscriber. So the frame is work, `isPending` reads the discriminant, and the drain replays a frame-only payload through `flushAtTick`. Dropping the frame in `deferring` instead would have made the docblock and the code disagree in the other direction.

**Refined by [ADR-097](./ADR-097-a-rule-id-is-a-closed-union.md), 2026-09-19.** Two things this paragraph settles were still being answered from the request rather than from the payload, and the quality pass over [#449](https://github.com/chahyasantoso/motion5/issues/449) found both. A frame-only deferral answers a deferred batch, which this decision already states, and it briefly answered an empty one, because the reason was chosen from the request's own seed list once both deferred reasons required a non-empty one. A reentrant call that deferred neither a seed nor a frame booked a drain although nothing was pending, which this decision never asked for and which decision two's own sentence refuses: a booking is a claim that a drain has work. Both are read from `deferredWork` now, and the frame-only answer reports under `reentrant-flush-deferred-frame`, because the seed-carrying rule owns its ids always and a frame is not a node to name.

**Decision three. A publication takes the seeds and retains a frame it did not reach.** This is the half decision two creates rather than closes, and it is decided here rather than discovered later. Once a frame is pending work, a live `flush` that cleared the whole payload would drop it, because `flush` has no parameter to reach a frame with and must not acquire one: ADR-082 made that separation structural. `retaining` answers what a publication leaves behind, which is a frame it has not reached and nothing else, and the `finally` that already books a drain for pending work books one for it. A frame the publication did reach is nothing to carry, which is the ordinary case of a drain replaying its own deferral.

**Decision four. A failed publication re-queues onto a live runtime only.** [#401](https://github.com/chahyasantoso/motion5/issues/401), option 1, for the reason the issue gives. [#378](https://github.com/chahyasantoso/motion5/issues/378) correctly moved snapshot derivation inside the boundary that re-queues drained seeds, and derivation runs the constructor-supplied `compose` and `interpolated`. Caller code may dispose the runtime and then throw, and the `catch` then put the seeds back onto an object whose phase is terminal, whose drain `bookingDrain` declines forever, and which therefore carried work nothing would ever publish for the life of the object. `requeuing` asks the phase first. ADR-083's claim is that `disposed` carries nothing; the payload is a field beside the phase rather than a member of it, so this guard is what says for the payload what the phase says for itself.

Option 2, folding the payload into the phase so the combination is unrepresentable, is the shape to prefer if the payload ever moves for another reason, and it is recorded here rather than taken: it would make `graph-runtime-state.ts` own the publication as well as the lifecycle, and the boundary between those two is worth more right now than one fewer guard. Option 3, refusing disposal from inside derivation, is refused on sight because [#388](https://github.com/chahyasantoso/motion5/issues/388) deliberately pinned that as legal.

**Decision five. Building a diagnostic and handing it to a host is one owner with one boundary, and a host failure is swallowed.** [#400](https://github.com/chahyasantoso/motion5/issues/400), option 1, which the issue itself prefers and calls the DRY answer. `#report` ended at `this.#onFlushError?.(diagnostic)`, which is host code with no boundary of its own, so a throwing sink left through whichever of five members was reporting. `#releaseBooking` is where that mattered: it runs after the deferred payload has been taken and before the publication boundary that would put it back, so a port whose `cancel` throws plus a host whose `onFlushError` throws dropped the drained seeds outright. [#378](https://github.com/chahyasantoso/motion5/issues/378) fixed that shape one statement further down; the same hole survived one statement further up. `diagnostic-report.ts` owns rendering an error and handing a diagnostic over, and one `try` there closes it for all five callers rather than four of them being fixed by a narrower change.

A host failure is swallowed rather than aggregated, and the record says so plainly because the issue asks it to. The diagnostic is answered to the caller and retained as `lastFlushError` before the sink is touched, so nothing the runtime knew is lost. A second diagnostic about a sink that has just thrown would be handed to that same sink, which is a loop rather than a report. ADR-039's clock boundaries are the precedent: a failure in injected code is labelled and contained where it happens, and it does not become the failure of the operation already in flight.

**Refined by [ADR-091](./ADR-091-retention-precedes-handover.md), 2026-09-16.** Two sentences above described an implementation this repository did not have. Retention did not precede the sink: it was an assignment from the boundary's return value afterwards, which is [#415](https://github.com/chahyasantoso/motion5/issues/415). And swallowing a host failure lost it rather than containing it, which is [#410](https://github.com/chahyasantoso/motion5/issues/410). What is kept is the refusal to hand a second diagnostic to the sink that just threw; what changes is that the boundary now returns nothing and the retained slots are the only answer.

**Decision six. A terminal runtime reports nothing new.** [#393](https://github.com/chahyasantoso/motion5/issues/393). `dispose` releases its booking before the phase goes terminal, so an ordinary disposal still reports a port that refuses to cancel, and the existing case that pins that stays green. What is refused is the reentrant case: a handler for one failure retires the runtime, and the failure still unwinding then files a diagnostic against an object that has stopped being able to act on one, so a reader is handed two claims that contradict each other. The guard is one line in `#report`, which is the one owner, rather than one per rule id.

That scope has a consequence worth stating rather than finding later. A drain failure discovered after caller code retired the runtime is not reported either, because the report would land on a retired object. That is the honest reading of `disposed` carries nothing, and it is the same trade ADR-083 already made for the booking and the mid-flush phase: a terminal runtime stops answering rather than answering carefully.

**Superseded as to retention by [ADR-091](./ADR-091-retention-precedes-handover.md), 2026-09-16.** The paragraph above is kept as the decision this record made, and [#409](https://github.com/chahyasantoso/motion5/issues/409) is that it decided two things at once. Delivery to a host is still refused once the phase is terminal, so the sentence holds for what a host receives; retention is no longer refused with it, so the sentence no longer holds for what the runtime keeps.

**Consequences.** No public export, diagnostic id or rule id moves, and `GraphRuntime` remains unexported from `packages/core/src/index.ts`, so `describeError` and `reportDiagnostic` are internal and the emitted declaration closure is unchanged. `describe` moves out of `graph-runtime.ts` rather than being copied, which takes that file further under the 30,000 byte sister-doc trigger instead of across it. `graph-runtime-state.ts` gains four exported answers and `GraphRuntime` gains no branch of its own for either question. `deferred-payload.test.ts` is the behavioural evidence and every case in it is red before this change; the state-space cases in `graph-runtime-state.test.ts` are red for the same reasons one layer down.

**Alternatives refused.** Freezing the shared empty set: refused, because it keeps a collection whose only purpose was to be empty, and a frozen `Set` still answers `add` by throwing rather than by being impossible to reach. Copying the pending set on every access: refused for the same reason at a cost. Making `isPending` a conjunction over the seed count and the frame: refused, because two fields answering one question is what produced #392, and a discriminant answers it once. Guarding the re-queue inside `GraphRuntime` rather than in the state module: refused, because the phase and the payload are that module's to relate. Wrapping every `#report` call site in its own `try`: refused as five owners of one question, which is the ADR-076 defect. Reporting a host sink failure through the same sink: refused as a loop.
