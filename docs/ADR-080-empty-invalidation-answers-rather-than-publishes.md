# ADR-080: An empty invalidation is answered rather than published

**Status:** Accepted, 2026-09-14

**Context.** [Issue #371](https://github.com/chahyasantoso/motion5/issues/371) traced `ProjectRuntime.invalidate([])` at `b49aec6908e753927303aad5fadd8782fec7600e` and found it paying for a real publication. `#invalidateSeeds` calls `this.#graph.invalidate(nodeIds)`, `GraphRuntime.invalidate` delegates to `flush`, and `flush` moves `#sequence`, raises `#flushing`, derives the snapshot and calls the publisher, with no empty short-circuit anywhere in the chain, so an invalidation that touches nothing opens a batch, notifies every batch subscriber and moves the sequence. This project had already decided that question twice: ADR-064 for a commit with no seeds, and ADR-078 for a recipe that staged nothing. [#370](https://github.com/chahyasantoso/motion5/pull/370) gave the decision one owner, `#publishSeeds`, which answers `emptyValueBatch(this.#graph.sequence)` for an empty list and hands anything else to the mechanics. Public `invalidate` is the only verb that takes a caller's seed list and does not reach that owner.

**Decision.** Public `invalidate(nodeIds)` publishes through `#publishSeeds` rather than through `#invalidateSeeds`. It keeps its liveness assertion, keeps the reentrancy refusal that makes it `value-batch-immediate` inside a batch, and keeps answering a real `PatchBatch`. What changes is that the empty case is constructed rather than published, decided by the member that already owns what an empty seed list means.

**Why not the spelling the issue asked for.** The finding proposes that the verb "check for an empty list up front and return the equivalent", and separately excludes folding it into `#flush`/`#publishSeeds` as already refused. Those two members answer differently and the exclusion holds for only one of them. `#flush` returns `void` and skips an empty list, so a fold into it would change a public answer and make a public verb's return optional, which is ADR-079's third decision and is not disturbed here. `#publishSeeds` returns a `PatchBatch` unconditionally and answers the empty one for an empty list, which is exactly the contract the issue asks to preserve: always a real batch, cheap to construct rather than cheap to skip. So the route the issue excluded is the route that satisfies the requirement it states, and the up-front check it proposed is what gets refused: it would put a second copy of an existing rule into the file whose previous slice existed to delete the third copy of a two-statement pair. Two owners for one question is the defect this project cares about most, and one of them being three lines long does not make it a smaller one.

**Why this is not fixed in `GraphRuntime`.** Short-circuiting `GraphRuntime.flush([])` or `GraphRuntime.invalidate([])` looks like the more general form of the same fix and would delete a working mechanism. `#scheduleDrain` calls `this.flush([])` precisely so that a deferred drain publishes what `#pendingSeeds` carried, and `flush` computes `effectiveSeeds` as the union of its argument and those carried seeds. An empty argument at that layer does not mean nothing to publish; it means publish whatever was queued. The emptiness of a caller's list is a project-tier question, and the project tier is where it already has an owner.

**Superseded in part by [ADR-088](./ADR-088-the-deferred-payload-is-one-closed-value.md), 2026-09-16.** Three mechanics named above moved. `#scheduleDrain` books the drain and `#drainScheduled` is the member that runs it. `#pendingSeeds` was a private set and is now a public getter over one `#pending` payload. And `flush([])` is one of two branches rather than the whole of the drain: since ADR-088 a deferral that carried a frame replays through `flushAtTick`. The decision this paragraph records does not move, and neither does its reason: emptiness is a project-tier question, and `ProjectRuntime.#publishSeeds` still owns it. [Issue #418](https://github.com/chahyasantoso/motion5/issues/418).

**What ADR-079 said, and what survives.** ADR-079's third decision refused the fold and reasoned from a premise: `invalidate([])` publishes today and answers the batch that publication produced. The premise was an accurate reading of the tree it measured and was never itself a decision. This record retires it rather than reversing the decision it supported: the fold into `#flush` stays refused, for the part of the reasoning that does not depend on what the empty case costs, which is that a public verb whose return became optional would hand its callers a second failure contract. A reader arriving at ADR-079's third decision should read the sentence about what `invalidate([])` costs as true of that head and superseded here.

**Consequences.** One observable change, and it is the point of the issue: `invalidate([])` no longer calls the publisher, no longer notifies subscribers and no longer advances `sequence`, and the batch it answers carries the sequence the graph is already on rather than the one a publication would have moved to. Nothing else moves. No exported type, member, refusal, diagnostic or rule id changes, no member is added or deleted, and `#invalidateSeeds` remains the only place in the file that names `this.#graph.invalidate(`, which is what `LV-5` asserts. The verb has no caller under `apps/` or in `packages/react`, and no test drove the empty case before this slice, so nothing shipped changes behaviour and the correction is priced as hygiene on unused public API.

`RA-171` is the evidence, red at the source head on an assertion rather than on a missing member: it drives `invalidate([])` and asserts the publisher was not called, the sequence did not move, and the batch is empty at the current sequence, then drives `invalidate(["rig/a"])` in the same rig so that a verb answering an empty batch for every list fails it too.

**Alternatives refused.** An up-front empty check inside `invalidate`, refused above as a second owner. A short-circuit inside `GraphRuntime`, refused above as the deletion of the deferred drain. Leaving it alone as the issue's own scope paragraph suggests, on the ground that no caller exists: a public verb with no callers is where a cost rule goes unnoticed, and the fix is one call rather than a member, so the cheaper thing to do is the correct one. Adding a standing rule to `docs/GUARDRAILS.md`: the rule is already there and in ADR-064, and what this slice found is a verb that never reached it, so a new bullet would restate a rule rather than earn one.
