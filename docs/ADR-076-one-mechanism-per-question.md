# ADR-076: One mechanism per question on the runtime surface

**Status:** Accepted, 2026-09-13

**Context.** Phase 3 of [issue #362](https://github.com/chahyasantoso/motion5/issues/362) read the whole public runtime surface and found two questions with two mechanisms each. `ProjectHandle.subscribe` and `ProjectHandle.subscribeNode` were the same call: both forwarded to `runtime.graph.registry.subscribeNode` verbatim, one line apart in `createHandle`, and the guide documented the first as "the same call under an older name", which is the discouraged-in-prose shape the guardrail refuses. `ProjectHandle.adopt` and `destroyAdopted` answered what `addTrack` and `TrackHandle.remove` already answered, and answered it more weakly: `adopt` returned a frozen `{ id, track }` a caller cannot ask about liveness, where `addTrack` returns a handle carrying a token, and removal was gated on a caller-invented owner object rather than on that token. ADR-026 already decided the token is the mechanism, and ADR-020 predates the handle entirely.

**Decision.** All three members are deleted, from `ProjectHandle` and from `ProjectRuntime`, with no alias and no deprecation window. Deleting the pair deletes the `owner` concept with it: `TrackEntry.owner`, the `#schemaOwner` sentinel and `#addTrack`'s `owner` parameter are gone, because they existed only to answer `destroyAdopted`'s ownership check. A node subscription is `subscribeNode`. A runtime track is added with `addTrack` and removed through the handle that call answers with.

**Alternatives rejected.** Keeping `subscribe` as a documented alias is the thing the guardrail names: a surface with two names for one call cannot be reasoned about for where a third belongs, and prose is not a mechanism. A dated retirement for `adopt` and `destroyAdopted` was refused for the reason a read-budget waiver carries a shrinking ceiling rather than a date: a date does not delete a member, it fails a build on a morning nobody picked, and it is satisfied by editing the date. Neither package is published and both consumers of this surface live in this repository, so there is no external caller a window would protect. Keeping the `owner` parameter on `#addTrack` in case something needs it again is a field with no consumer, which this project deletes and then refuses.

**Consequences.** Breaking, by subtraction, on a private `0.0.0` package. Every reader moves in the same change, because a deletion with no alias is finished at every reader before the push and `typecheck` is the gate that proves it: twenty-four modified test files, one demo app, the graph benchmark and four documents, two of which no gate reads. Two claims travelled with the deleted pair and are restated rather than dropped: `SchemaTransaction`'s docblock named `adopt` and `destroyAdopted` as the structural verbs absent from that surface and now names `ProjectHandle.addTrack` and `TrackHandle.remove`, which is the same fact about the same commit, and `RA-85` asserts it through those two members instead. The owner gate is not replaced, because a stale handle already refuses uniformly under ADR-056. The benchmark keeps its `Adoptions` and `Destroys` output labels on purpose: `docs/BENCH-PHASE5.md` cites its numbers by those labels, and a recorded measurement whose labels moved is no longer comparable to the run that produced it.

**Evidence.** `RA-155` through `RA-157` in `packages/core/test/integration/one-mechanism-per-question.test.ts`. Absence is asserted with `"name" in object`, on `RA-16`'s shape, so each case typechecks on both sides of the deletion and fails on an assertion rather than on a compile. Each asserts the surviving spelling is present in the same rig, because a probe against a mistyped receiver answers absent for every name, and each asserts the accepting direction, because a case whose subject is a deletion is green against the deletion alone. `packages/core/test/integration/project-handle-surface.test.ts` keeps owning the handle's total key list, which is where a member added later lands first.

**Also in this slice, and not a decision.** `docs/guide/api-reference.md` and `docs/guide/runtime-changes.md` both listed `signal` as a member of `MotionHandle`. The source declares no such member, deliberately: signalling a Motion is the composition root's question, answered by `ProjectHandle.signal`, and the runtime that holds those trigger tokens holds no Motion instance to signal. Both lists are corrected, and a convenience-API pass would otherwise have propagated that line into a real member.
