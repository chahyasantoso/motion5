# ADR-067: A commit boundary owns the teardown a hook asked for, and the release is deferred while the decision is not

**Status:** Accepted, 2026-09-05. [Issue #303](https://github.com/chahyasantoso/motion5/issues/303).

## Context

ADR-064's amendment of 2026-09-04 closed the case where a caller entered `#apply` on a runtime that was already disposed, and in its **Stated on starting rather than on running** paragraph it named the case it did not close: a host hook applied inside `#apply` is caller code too, and one that disposes the runtime mid-commit would still reach the graph on a dead runtime. It said so explicitly rather than by omission, so the invariant it stated would not be read as covering this.

This is that case. It is a new record rather than a fifth amendment to that one, because ADR-064 owns the schema transaction and the hooks a commit derives from what it commits, and the question here is commit lifecycle against resource lifetime: when a runtime is allowed to say it is dead, and when it is allowed to let go of the things it holds. None of ADR-064's four amendments asks that, and the paragraph above stays true of the slice that wrote it, so nothing in it goes stale.

The gap was named and undescribed rather than known to be wrong, which is what the issue asked to be measured first. It is two shapes, not one.

**Disposal from an effect, before `replaceGraph`.** `dispose()` set its flag, detached every instance, cleared both retained maps, disposed the graph and called `disposeComposition()`, all of it synchronously inside the hook. Control then returned to a loop that knew nothing about any of it. Every remaining effect ran, so `compileTrack`, `stageTrack` and `replaceMotionTrack` reached a composition whose teardown had already returned, and anything they built became unreachable by any later release, because `dispose` is one-shot. `replaceGraph` then reached `GraphRuntime`'s own liveness check and threw, the `catch` reverted in apply order and handed that same torn-down composition a `disposeTrack`, a `destroyMotion` and a `staged.rollback()`, and `Error: GraphRuntime is disposed.` reached the caller. That last part is the defect issue #288 corrected for a recipe, arriving one indirection further in: it names the layer that noticed rather than the owner that decided. `#adoptMaps` was never reached, which is the one thing that did not go wrong.

**Disposal from a settle step, after `replaceGraph`.** Not in the issue's own description, and strictly worse. `addMotionTrack`, `removeMotionTrack`, `disposeTrack` and `staged.commit()` are all injected seams and all run outside the try, after `#adoptMaps` and after the graph accepted. The next settle step is `#mountNode`, which calls `GraphRuntime.attach`, which asserts liveness, so `Error: GraphRuntime is disposed.` escaped `#apply` with the commit already adopted and with no rollback list at all, because a settle step has no revert by design.

So a mid-commit disposal continued into `replaceGraph`, into map adoption, into the settle steps and into the invalidation. Only `replaceGraph` happened to stop it, and it stopped it on behalf of a layer that does not own this decision.

## Decision

`dispose()` is never refused and never interrupts a commit. It is honoured immediately as an **answer** and deferred as a **release**: from the line it is called on, every public member refuses `ProjectRuntime is disposed.` and every handle answers stale, while the graph, the retained pair and the composition stay alive until the commit that was in flight has finished unwinding. The release then runs exactly once, at the boundary that owns the unwind, after the rollback and after the settle phase.

**A refusal and a release are two questions, and only the first may be answered inside a callback the owner is still inside.** That is the whole of it, and it is an argument rather than a preference, so it is worth stating as one. The rollback owns composition resources that the release would otherwise double-free or leak. `disposeTrack`, `destroyMotion` and `staged.rollback()` are the inverses of `compileTrack`, `createMotion` and `stageTrack`, and every one of them reaches the composition. A release that runs where `dispose()` was called therefore guarantees the unwind is wrong in one direction or the other, no matter how `#apply` is arranged internally: either it hands a torn-down host the inverse of effects it can no longer apply, or it skips the inverses and leaks everything those effects built. The choice between double-freeing and leaking is not a contract, so the release moves and the decision does not.

**`dispose()` stops owning resource release and starts owning the decision to release.** `#teardown()` is the release, and it is the previous body of `dispose()` moved rather than rewritten. `dispose()` sets the flag, and then either calls `#teardown()` or records that the boundary must. `#apply` is the only other member allowed to call it.

**Three pieces of private state, one reader each.** `#committing` is a depth rather than a flag, because a hook can re-enter `#apply` through a public entry point and a flag cleared by the inner `finally` would release while the outer commit was still unwinding; a counter costs one character and declines to introduce a defect this record is not about. That reentrancy is a separate defect and it is [issue #307](https://github.com/chahyasantoso/motion5/issues/307) rather than this record's to fix, but the state it needs exists after this slice. `#pendingTeardown` is set only by `dispose()` and cleared only by `#teardown()`, which is what makes exactly-once true by construction rather than by two guards agreeing. And `#teardown()` itself.

**The boundary is asked in exactly three places, and the count is the design.** Each one has its own reason, and none of them is symmetry.

After `#derive`, because `#needsTimelineBuild` calls `#resolve`, which is the injected `resolveKeyframes` seam, so caller code runs before the first effect is applied. Nothing has been applied at that point, so it refuses with nothing to roll back, and that is also why the depth is raised ahead of the derivation rather than ahead of the loop.

After every `effect.apply()`, which is issue #288's rule applied one indirection out rather than restated one noun wider: a precondition asserted before a callback is not a precondition on what follows it. It is a plain `#assertLive()`, the member that already exists, so there is no second message and no second error type, and the throw lands in the existing `catch`, so the existing rollback list and `rejectAfterRollback`'s existing precedence do the work unchanged.

Before the `invalidate`, and **nowhere inside the settle loop**. The asymmetry is deliberate and it is the part of this decision most likely to be read as an oversight. A settle step has no `revert` because it is not allowed to fail, so abandoning that phase halfway leaves a staged Track neither committed nor rolled back, a Motion registered against a node that never mounted, and an evicted node still in `#instances`: a leak dressed as a refusal. Because the release is deferred, the graph and the composition are still live there, so `#mountNode`, `evictNode`, `addMotionTrack` and `staged.commit()` all still work; the phase completes, and the release that follows cleans up what it produced. The flush is the one thing skipped rather than completed, on the reason ADR-064's amendment of 2026-09-03 already gives for the empty-seed guard sitting where it does: a batch nobody can read still opens, notifies every subscriber, moves the sequence and drains whatever seeds a deferred flush was holding.

**`GraphRuntime is disposed.` becomes unreachable through a commit.** That is the sharpest statement of what changed, and it is the property to check a future edit against. `GraphRuntime` is never called after its own `dispose()` from this path, because the release is the last thing that happens and every graph call precedes it.

**`#liveOf` gains one term, and that is the second half of the slice.** The deferral opens a window in which the runtime is disposed and the retained maps are still full, and every settle-phase hook runs inside it, so the window is observable. Until now "a disposed runtime's handles are all stale" held only because `dispose()` happened to call `.clear()`, which ADR-064's amendment of 2026-09-04 states as a fact about the mechanism. So the one member both handle ladders already share answers `undefined` for a disposed runtime, by decision. It adds no throw anywhere, so ADR-056's refusal of `#assertLive` inside the reading ladder is untouched: `live` still may never throw, it just answers `false` for a decided reason rather than a side-effectual one. `#writableEntry` and `#writableMotion` still ask `#assertLive` first, so issue #298's contract that a write reports the disposal rather than the staleness is unchanged.

**ADR-056 needs no amendment**, and that is a reading rather than an omission. Its second amendment's invariant is that after `dispose()` every reading member of a `MotionHandle` refuses with `StaleMotionHandleError` carrying the captured motion id, and that is exactly as true after this slice as before it. Only the mechanism behind it moves, and the mechanism was never that record's claim.

**`dispose()` no longer clears `#open` on the deferred path**, and does not need to. `#commit` returns early whenever `#open` is set, so `#open` is always `undefined` inside `#apply` and the window can only ever exist while no recipe is open. ADR-056's measured claim that a disposed runtime never has an open recipe therefore survives, and `#assertLive` and `#refuseInsideRecipe` still cannot both have something to say. Stated here rather than left to be re-derived by the next reader of that claim.

## Alternatives rejected

**Refusing `dispose()` during a commit.** The cheapest change available and the wrong one, for the reason ADR-064's amendment of 2026-09-04 already gave when it refused the same thing for a recipe: teardown has to be reachable from a `catch`, and a hook that catches its own failure and tears the project down would get a refusal about the teardown in place of the error it was handling. `RA-110` exists to keep that refused, and this would have contradicted it one indirection out.

**Immediate release plus an aborted commit.** The shape that looks right and cannot be made right, for the argument in the Decision above. It is worth naming as a refusal rather than passing over, because it is the design a reader arrives at first: guard the loop, roll back, report the disposal. Every part of that is in this decision except the timing of the release, and the timing is the only part that decides whether the rollback is correct.

**An `#assertLive()` in every effect and every hook callback.** The issue forbids it and the guardrails own why: an order enforced by convention at n call sites is enforced at the first of them only, and the n+1st, added later, is wrong by default. It is also the defect issue #298 deleted seventeen copies of.

**A dedicated commit-state guard object beside `ProjectRuntime`.** The issue leaves this open if the evidence shows `#apply` cannot own the ordering. The evidence shows it can: the state is a depth and a flag, both read by one member, and the only thing that needs to know a commit is in flight is the member running the commit. A second object would be a second lifecycle owner for a two-field question, which is what the issue's own ownership constraints refuse.

**Guarding between settle steps, for symmetry with the effect loop.** Refused on the leak, and named as a refusal rather than left as an omission: the two phases are asymmetric because one has a revert and the other does not, and a guard that treated them alike would be symmetry chosen over correctness.

**Draining the deferred release at the end of `#commit`.** `#commit` returns early while a recipe is open, so a release drained there would never run for the `edit` path and would run at the wrong depth for a nested commit. The boundary belongs to the member that has the `try`.

**Widening the deferral to the four direct-hook write paths in the same slice.** `#writeValues`, `#recompileKeyframes`, `#setTrigger` and `#setStagger` each call a hook and then mutate the retained pair in place, so a hook that disposes leaves a disposed runtime holding entries. That is the same defect on the one family of paths that never reaches `#commit`, and it is [issue #305](https://github.com/chahyasantoso/motion5/issues/305) rather than this slice. Two reasons for the split. Those paths return a `PatchBatch` a caller reads, so what they answer after a disposal is a decision this record does not have to make in order to be correct about a commit; and the mechanism here is meant to be widened by **wrapping** a second boundary in it rather than by copying a guard into four members, which is the shape issue #298 deleted.

## Consequences

No public surface moves: no export, type, schema, signature, message or `ruleId` changes, and `dispose()` keeps its signature and its one-shot contract. What changes is which error a caller reads when a commit's hook disposes, and that a caller reads no error at all when a settle step's hook does.

A caller may now rely on three things it could not before. A composition hook may dispose the runtime from inside a commit without leaking what the applied effects built and without the host being asked to release the same resource twice. The error it reads names `ProjectRuntime` rather than `GraphRuntime`. And `disposeComposition` is called exactly once, after the unwind rather than in the middle of it.

The settle phase is now depended upon to complete, which promotes an assumption into a requirement: nothing enforces that a settle step cannot fail, and what a throwing one leaves behind is undecided. That is [issue #306](https://github.com/chahyasantoso/motion5/issues/306), filed rather than absorbed, because this record relies on it being a contract and a reliance that nothing measures is the kind of justification the guardrails call load-bearing.

[GUARDRAILS.md](./GUARDRAILS.md) gains one rule and one only, the general form of the argument above. The re-ask in the effect loop earns nothing, because the rule it applies is already there from issue #288 and restating it one noun wider would be drift with extra steps.

## Evidence

`RA-114` through `RA-117` in `packages/core/test/unit/runtime/structural-commit-path.test.ts`, which already owns `RA-1` through `RA-7`, already injects every hook a commit reaches, and already carries the one ordered journal this measurement needs. Pushed ahead of the source, so the red run is its own and can be cited by id.

The rig gains a disposing-hook config, a `replaceMotionTrack` line, an optional `stageTrack` seam and a `disposeComposition` line. That last one is the instrument rather than a convenience: a rollback step that reached a torn-down composition and one that reached a live composition are indistinguishable by any counter and differ by one line in a journal. The staging seam is wired only when a case asks for it, because the seven cases above were written against a rig without one.

- `RA-114` the effect-phase contract. The message is `ProjectRuntime is disposed.` and not an `AggregateError`, which is how it says the rollback itself did not fail; the journal reads compile, dispose, composition-dispose in that order; no settle-phase line appears at all, which is where non-adoption is measured rather than in a second assertion; and a second explicit `dispose()` adds no second teardown.
- `RA-115` precedence when a hook disposes and then throws. The caller gets the hook's own error by identity rather than the disposal, the staged replacement is rolled back and never committed, the effect that threw is not reverted because an effect counts as applied only once its call returned, and the rollback line still precedes the teardown.
- `RA-116` the window is closed. It reads `live`, `definition`, `motion()` and `mount()` from inside the disposing hook, after `dispose()` returned. Green on both sides for two different reasons, which is `RA-110`'s shape: before, because the maps were already empty; after, because `#liveOf` reads the flag. It is a lie detector for the deferral rather than evidence of the fix, and it is the case a deferral that moved the release without moving that answer fails.
- `RA-117` the settle-phase contract and the accepting direction. Nothing is thrown, the handle comes back, the settle phase completed, the flush was skipped, and the node the following settle step mounted is detached by the release. Written through an outcome helper rather than a bare call, for the reason `schema-transaction.test.ts` gives about `RA-109`: a red run has to fail on an assertion that disagreed rather than on a call that could not finish.

Three of four red, predicted and reported rather than engineered. `RA-116` cannot fail before the slice and the file says so, which is the guardrail against padding a red count by asserting less in the case that could not fail.
