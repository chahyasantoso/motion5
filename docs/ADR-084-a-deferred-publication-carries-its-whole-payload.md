# ADR-084: A deferred publication carries its whole payload, and a booking is a claim about the scheduler

**Status:** Accepted, 2026-09-16

**Context.** Five findings arrive from the quality passes over [#375](https://github.com/chahyasantoso/motion5/pull/375) and [#386](https://github.com/chahyasantoso/motion5/pull/386), read at `1af7580557b0ad65a44c4216a0fde7170f33e203` and `d69b38415299822bb2ccdd085941c23aeaa27310`. They are one slice because they are one seam read from five sides: what a reentrant call leaves behind, and who owns it afterwards. [Issue #380](https://github.com/chahyasantoso/motion5/issues/380) is the payload, and it was half a payload. [Issue #389](https://github.com/chahyasantoso/motion5/issues/389) is the booking, and it was a claim about the wrong thing. [Issue #382](https://github.com/chahyasantoso/motion5/issues/382) is the precondition that guards the publication the two of them feed. [Issue #387](https://github.com/chahyasantoso/motion5/issues/387) is the gap between what ADR-083 claims about the state unions and what their types enforce. [Issue #388](https://github.com/chahyasantoso/motion5/issues/388) is the one ordering ADR-083 calls load-bearing and no test drove. None of them was introduced by #375 or #386; both refactors made them legible by giving the transitions names, which is the outcome those slices were for.

**Decision one. The frame number travels with the deferred seeds, and is recorded by the publication that runs.** `#deferIfFlushing` queued the seeds and dropped the tick, because the drain publishes through `flush([])` and that verb has no tick parameter at all. So a deferred `flushAtTick` kept its work and lost the frame it was asked to reach, and `#lastTick` stayed where it was for a frame the runtime had been told about. #380 offers three answers and this is its second: the pending state grows a frame number, and the drain replays through `flushAtTick` when it carries one. The first answer, refusing deferral for the clock verb, is refused below because it drops work. The third, declaring the loss as the contract, is refused because a frame number that is asked for and silently discarded is not a contract, it is an unobserved behaviour with a docblock.

```ts
export interface PendingPublication {
  readonly seeds: ReadonlySet<string>;
  readonly tick: number | undefined;
}
```

**The rule #380 asks for, when two deferred frames arrive inside one flush: the later wins.** A frame number only ever advances, so replaying the earlier of two would be refused by `#assertTick`, which is the guard the deferral exists to preserve rather than to work around. A deferral that names no frame, which is every `flush`, leaves whatever frame is already pending alone rather than erasing it: `flush` cannot name a frame and must not answer for one. That is why `#deferIfFlushing` takes the tick as an optional parameter and not a required one. The optionality is a property of the two verbs, one of which has no frame to hand over, and not a choice offered to a caller: `flush`'s call site says nothing, `flushAtTick`'s states its own. ADR-082 retired an operation selected by argument presence on the public surface, and that is untouched here.

**Why a pending frame cannot be overtaken.** The obvious worry is a pending frame that a later publication already passed, which `#assertTick` would then refuse and which would strand the seeds behind it. It cannot happen, and the reason is worth writing down rather than guarding: the only writer of `#lastTick` is `#advanceTick`, whose only caller is `flushAtTick` on the path that goes on to call `#flushSeeds`, and `#flushSeeds` takes the pending payload as its first act. So any publication that moves `#lastTick` past a pending frame also consumes the payload that held it. There is therefore no staleness branch in `#drainScheduled`, because a branch that cannot be reached is a claim asserted only by the code that has it.

**Decision two. Validity is asked before reentrancy, and recording stays separate.** `flushAtTick` now calls `#assertTick` before `#deferIfFlushing`, so a frame this runtime could never reach is refused whether or not a publication happens to be open. Without it, a reentrant call could queue a non-finite or regressive frame that only failed later, inside a scheduler job, reported as a `flush-failure` under a rule that names the wrong thing. `#assertTick` owns validity and `#advanceTick` remains the one write to `#lastTick`; the question is asked twice, by one owner, which is delegation and not duplication. ADR-076 is about two owners of one question, not about one owner answering twice.

**Decision three. A booking is a claim about the scheduler, so a publication that consumes a drain cancels the job it consumed.** `#flushSeeds` released the booking on every publication, including one that no drain scheduled, while the `Cancel` handle `Scheduler.schedule` answers with was discarded. So a direct `flush` between a booking and the scheduler running it took the pending seeds, lowered the booking, and left the job outstanding; the phase then said nothing was booked, so the next deferral booked a second job for one drain. #389 names the two ways out, and this is the first: the `Scheduler` port already answers with a handle carrying `cancel`, so the booking and the handle are held together and released together by one member, `#releaseBooking`. The second way out, declaring the booking a claim about the phase only and accepting a redundant job, is refused: a runtime whose own state is wrong about the outside world is the defect this project cares about most, one field larger.

`scheduler-reentrancy`'s coalescing case is the oracle #389 names, and it does not move: one booking is still one job, because coalescing was never the thing that was wrong. What moves is the count of _outstanding_ jobs across a publication, which was two for one drain and is now one. `dispose` cancels for the same reason, before the phase goes terminal. `#drainScheduled` keeps its refusal on the discriminant, because a port may decline to cancel and a job that runs anyway must still find a retired runtime that says no.

**Why the phase is lowered before the port is touched.** `#releaseBooking` assigns `unbookDrain(this.#phase)` and then calls `handle.cancel()` inside a boundary. A `cancel` that throws is out of contract, but if it did, the alternative order would leave this runtime believing it still owes a drain that nothing will ever run, which is a wedge rather than a diagnostic. The failure is reported under `scheduler-failure`, the rule that already owns scheduler trouble, rather than swallowed or given a rule id of its own.

**Decision four. Both state unions are branded, so their illegal combinations are unassignable rather than merely unreached.** ADR-083's decisions one and two claim that the combinations the six retired booleans could spell are unrepresentable. #387 found that claim stronger than the types made it: excess-property checking reads a fresh object literal and not a value arriving through a variable, so a disposed phase carrying a booking, and a cold memo still carrying the membership revision `replaceGraph` used to leave behind, were both assignable through one intermediate const. Nothing observable was at risk, because both fields are private, the four live phase values are interned and unexported, the module is not re-exported from `packages/core/src/index.ts`, and every write goes through a transition. It matters anyway, because moving an invariant from the call graph into the type was the whole point of that slice, and "unreached" is the weaker property its own decision one argues against.

Two `unique symbol` marks, declared and never exported, sit on the variants, and `mintPhase` and `mintMemo` are the only expressions in the program that assert them. No other module can name the key, so no other module can spell a phase or a memo at all, which also answers the wider question #387 raises about who may construct one. The brands are phantom: nothing is assigned at runtime, so the interned values are byte-identical to what they were and a transition is still a lookup rather than an allocation.

**Why a brand rather than an optional `never` exclusion.** #387 offers both. An exclusion such as `readonly drain?: never` on `DisposedPhase` closes the assignment and opens something else: `drain` then exists on every member of the union, so reading `phase.drain` off an un-narrowed `RuntimePhase` becomes legal and the existing compile-time case that forbids it stops being a diagnostic at all. That trades one arrow for another, and an unused `@ts-expect-error` is itself an error, so the exclusion would have had to delete evidence to add evidence. A brand keeps both: the property is still absent from the variant that does not carry it, and the variant is still closed to anything this module did not mint.

**Decision five. The precondition is asserted, not stated.** `#flushSeeds` owned publication mechanics for both verbs and stated its one precondition in prose, on the argument that a second copy of a decided question is a second owner of it. The ownership argument is sound and it is kept; what #382 corrects is the conflation. An assertion is not a second owner of a decision, it is the check that the decision held, and those are different things. The check is the first statement in the member, before the pending payload is taken, before the booking is released and before `#sequence` moves, because the cost of it being wrong later is a violation detected after the state it needed was thrown away: mutated state and a misattributed error, which is the worst shape a precondition failure has.

It is unreachable today, and one branch is what that costs. `graph-publisher.ts` carries several guards of exactly this kind, each labelled as a defensive invariant rather than a live path, so this is the house style and not an exception to it. The structural alternatives #382 prefers are refused below.

**Failing-first evidence.** `packages/core/test/unit/runtime/deferred-publication.test.ts` is new, and two of its cases are red before this change for reasons worth stating, because they are what makes this a behaviour slice rather than a refactor. The frame case reads `runtime.tick` after the drain publishes and got the frame before the deferred one. The booking case counts the scheduler's own outstanding jobs across a publication and got two for one drain. Neither is observable through a patch, which is why both survived a full quality pass over the code that contains them and were filed rather than seen. Beside them: two deferred frames coalesce to the later, a deferral naming no frame still publishes through `flush` and is deliberately green on both sides, a `cancel` that throws is reported without wedging the booking, and the #388 case disposes a runtime from inside an active publication and asserts through the public surface only, which is what #376's acceptance asked for. It pins that the in-flight publication finished, that no second batch was published, that `pendingSeeds` is empty, that the runtime still refuses `flush`, that no diagnostic was reported, and that the job the scheduler was holding is gone rather than merely refused when it runs.

`packages/core/test/unit/runtime/graph-runtime-state.test.ts` grows the two compile-time cases #387 asks for, and they read the assignment rather than the property, which is the shape its existing three arrows all pass over. They are red before the brands for the honest reason that the assignment they forbid compiles.

**Consequences, and the two behaviour changes named.** No public surface, no exported type or member, no diagnostic id and no rule id retires. Two behaviours move, deliberately and narrowly. A deferred clock publication now advances `#lastTick` when it publishes, where it previously did not advance it at all; `runtime.tick` therefore answers the frame that was asked for rather than the one before it, and the clock's regression guard is measured against a frame the runtime actually reached. A publication that consumes a drain now cancels the job it consumed, so a scheduler holds one job per drain rather than up to two; nothing published twice before and nothing publishes twice now, so no batch, patch or sequence moves. One diagnostic message is added, under the existing `scheduler-failure` rule, for a port that refuses to cancel. `#assertTick` is added beside `#advanceTick`; `#releaseBooking` is added and is the only caller of `unbookDrain`, where three members called it before. `#pendingSeeds` is deleted and `#pending` and `#drainHandle` are added, so one field becomes two and the second of them is the port's own handle rather than a copy of anything.

**Where the reasoning lives.** `graph-runtime.ts` goes from 23,138 to roughly 27,600 bytes, so it stays under the 30,000 that would oblige a sister document, and the margin is stated rather than assumed because #376 asked for that number and this slice spends part of it. `graph-runtime-state.ts` goes from 7,141 to roughly 11,100. Reasoning that would have pushed the source past its budget lives here instead, which is what this record is for. ADR-082 and ADR-083 are deliberately not edited: this project supersedes a record with a record rather than amending a decided one. ADR-083's "one case worth naming" is answered by decision three above, and ADR-082's ordering for a reentrant clock call is preserved rather than reversed, since the frame is still not recorded by the call that publishes nothing.

**Alternatives refused.** Refusing deferral for the clock verb, #380's first option: a reentrant `flushAtTick` would throw, `#flushTick`'s boundary would convert that into a `flush-failure` diagnostic, and the seeds would be dropped rather than deferred. It trades a lost frame number for lost work, which is worse. Declaring the dropped frame as the contract, #380's third option: refused because the regression case it owes would then pin an unobserved behaviour as a decision. Growing a `#pendingTick` field beside the seed set: refused as the ADR-076 defect in miniature, since "what was deferred" would have two owners; the payload is one value for the same reason the memo carries its whole key. Making `#flushSeeds` structurally unreachable by having `#deferIfFlushing` hand back a publication continuation, #382's stronger fix: refused because it allocates a closure per publication on a path ADR-083 keeps allocation-free, and the variant that merges both verbs into one private taking an optional tick reintroduces at the private level the shape ADR-082 retired at the public one. Threading a minted publication permit through `#flushSeeds` was considered for the same purpose and refused as machinery that states an invariant less clearly than the assertion does. An optional `never` exclusion instead of a brand: refused above, because it deletes a diagnostic to add one. A fourth `draining` phase, or any return to boolean lifecycle state: still refused, exactly as ADR-083 decision three has it, and #387 explicitly does not disturb it. Fixing any of this inside #386: refused there, correctly, by a slice whose whole claim was that nothing observable moved.
