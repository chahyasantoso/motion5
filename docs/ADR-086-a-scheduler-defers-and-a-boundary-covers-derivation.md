# ADR-086: A Scheduler defers, a publication boundary covers derivation, and a diagnostic names what happened

**Status:** Accepted, 2026-09-16

**Context.** Three findings from the quality pass over [#375](https://github.com/chahyasantoso/motion5/pull/375), read at `1af7580557b0ad65a44c4216a0fde7170f33e203`. They are one slice because they are one path read from three places: what happens to deferred work between the moment a publication takes it and the moment it is published. [Issue #377](https://github.com/chahyasantoso/motion5/issues/377) is the port that hands it back too early. [Issue #378](https://github.com/chahyasantoso/motion5/issues/378) is the boundary that does not cover the whole of the handover. [Issue #383](https://github.com/chahyasantoso/motion5/issues/383) is what the runtime tells a host it did with it. None was introduced by #375; splitting `flush` from `flushAtTick` and giving the publication mechanics one owner is what made all three legible.

**Decision one. The `Scheduler` port states that a job must not run before `schedule` returns, and one decorator enforces it.** The port declared `schedule(job, options?): Cancel` and said nothing about when the job runs, so a scheduler that ran its job inline satisfied the contract and broke the runtime: `#scheduleDrain` books from inside the publication that deferred, the job lowers that booking as its first act, and a `flush` from inside the same publication defers and books again. Unbounded recursion to a stack overflow, not a slow drain. The booking is the obvious guard and cannot be one, because it is lowered before the call it was passed to has returned.

#377 offers two answers and this takes its first, for the reason the issue gives: the runtime depends on deferral in more than one place, so the dependency belongs in the port's own contract rather than in a reentrancy latch the caller maintains. ADR-038 had already decided the pass boundary for `createMicrotaskScheduler`, where a reentrant schedule lands in the next pass and there is one host enqueue per pass, and it even says `GraphRuntime.#scheduleDrain` assumes that boundary. What was missing is that the assumption was recorded in an ADR about one adapter and nowhere in the interface a future adapter reads.

**The enforcement is a decorator, not a branch in each consumer.** `deferredScheduler` wraps the injected port once, in `GraphRuntime`'s constructor, and the runtime below it is written against a port that defers. A rule re-asked at every call site has as many owners as it has callers, which is the ADR-076 defect, and the alternative #377 offers second, not lowering the booking until the drain has published, is exactly that shape: it makes one member reentrancy-safe and leaves the contract unstated for the next member that schedules.

**A violation refuses the job rather than running it, and leaves through `schedule`.** Running it is the recursion, so refusing is the fix rather than a symptom of one. The refusal is a `TypeError` out of `schedule`, which lands in the boundary `#scheduleDrain` already has for a port that refuses work: the booking is released, one `scheduler-failure` diagnostic is reported, and the deferred seeds stay in `#pending` for the next publication to carry. That degradation is not invented for this decision. It is exactly what a runtime constructed with no scheduler already does, and `publisher-reentrancy` already tests it, so a port that breaks its contract falls back onto a supported path rather than onto a new one.

Recursion is bounded at one nested call. The wrapper refuses every later `schedule` once it has seen a job run inline, so a port that swallows the first refusal cannot buy a second inline pass with it, and a runtime whose port is hostile still ends its turn.

**Why not `assertScheduler`.** It is a shape check, and no shape check can see when a job runs. The two live beside each other because they answer different halves of the same contract: one refuses an object that is not a scheduler, the other refuses a scheduler that is not deferring. `deferredScheduler` is not exported from `packages/core/src/index.ts`, so the public surface is unchanged; a host that composes its own port reaches the guard the moment it hands the port to a runtime.

**Decision two. The publication boundary begins before derivation, because derivation runs caller code.** `#flushSeeds` took the pending payload, cleared it, released the booking, and then derived the snapshot, all before the `try` whose `catch` exists to put the work back. `#snapshotFor` is not bookkeeping: on a cold memo it builds publisher nodes, and `#publisherNode` calls the constructor-supplied `#compose` and `#interpolated`. So injected caller code ran in the one window where the drained seeds existed nowhere, and a supplier that threw dropped them.

The fix is the issue's own first recommendation, and its two notes about what must not move are honoured. `#sequence += 1` moves inside the boundary and nothing observable moves with it. `beginFlush` does not move earlier, because the reentrancy window is a decided thing and widening it would let a subscriber-triggered call be deferred by a publication that has not begun. `endFlush` is total and terminal-safe, so a derivation failure leaves the phase where it was rather than walking an idle runtime somewhere else.

The requeue carries no frame the publication reached, and that half is unchanged: `flushAtTick` records the frame before `#flushSeeds` is called, so a frame the failing call had already reached was consumed by it and re-queuing one would claim a frame twice. A frame the publication never reached is the other case and is kept rather than dropped: `retaining` leaves a later deferred frame pending and `requeuing` preserves it, so a direct `flush` that fails over a frame it could not have published re-queues its seeds beside that frame. Issue #417 is that this sentence used to state only the first half, which reads as a rule that `retaining` breaks. See ADR-084 and ADR-088. The precondition assertion ADR-084 added stays outside the boundary, deliberately: a precondition failure must not re-queue, because the seeds it would restore belong to a caller that should never have reached the member.

**Why not a `#drainInto` owner.** #378 sketches one, pairing the drain with its restore. It is a real option and it is refused here as machinery: the pair is already two statements in one member, and the boundary is what makes them a pair. A named owner would state the same invariant less directly and add a member to a file spending its remaining read budget.

**Decision three. The deferral diagnostic names a publication, and says which future the work has.** The message said the flush "was queued as one follow-up invalidation for the scheduler". `invalidate` is an operation ADR-082 retired from this tier, so a reader tracing the diagnostic looked for a member that is not there; `invalidate` now belongs to `ProjectRuntime` one layer up. And "for the scheduler" presumed one, while the runtime that receives this diagnostic most often in the existing evidence is the one `publisher-reentrancy` builds with no scheduler at all.

#383 asks for the two cases to be distinguished where they diverge, and only `#scheduleDrain` knows, so it answers a boolean and `deferredBatch` takes it. The answer is `#drainHandle !== undefined` rather than a fourth branch: the port holds a job for this runtime exactly when that field is set, so a booking already held answers true where `bookingDrain` declined for coalescing, a disposed runtime and an absent port answer false, and a `schedule` that threw answers false because its boundary released the handle. One field, read once, and no new state.

The rule id `reentrant-flush-deferred` does not move, because it was always accurate, and neither do the severity or the path. This is a message change and it is declared as one: no rule id, no diagnostic id and no public surface retires.

**Failing-first evidence.** `packages/core/test/contract/scheduler-deferral.test.ts` is new. Its runtime case is red before this change by exhausting the stack, and it pins the bound, the reported rule, and that the refused work is still published by the next flush. Three unit cases beside it cover a deferring port passing through with its own handle, an inline job refused without running, and a port that swallows the refusal getting no second pass.

`packages/core/test/unit/runtime/publication-boundary.test.ts` is new and is the evidence #378 asks for: a `compose` supplier that throws once, asserting that the drained seeds still name themselves after the throw and that the follow-up publishes both. It colds the memo through `replaceGraph` first, because a warm memo never reaches the supplier.

`packages/core/test/unit/runtime/deferred-flush-diagnostic.test.ts` is new and reads both messages. The no-scheduler case is red before the change for the honest reason that the message named a scheduler that runtime does not have, and a third case asserts that neither message names a retired verb while the rule id, severity and path are unchanged on both sides.

`scheduler-reentrancy`'s existing cases are the oracle for the two things that must not move: one booking is still one job, and a port that throws from `schedule` is still retried by the next deferral and still reported under `scheduler-failure`.

**Consequences.** No public surface: `deferredScheduler` and `INLINE_JOB_MESSAGE` are added to `ports/scheduler.ts` and neither is named by `packages/core/src/index.ts`, so the exports map and the declaration closure are unchanged. `#scheduleDrain` answers `boolean` where it answered `void`, and it is private. `deferredBatch` takes a third parameter, and it is module-local.

**Three behaviours move, all narrow.** A scheduler that runs its job inline is now refused and reported instead of recursing, which no shipped adapter does. A failure inside snapshot derivation now re-queues the seeds the call had drained instead of dropping them, and rethrows exactly as before. The deferral diagnostic carries one of two new messages instead of one wrong one. No batch, patch, sequence or frame number moves in any of the three.

**Where the reasoning lives.** `graph-runtime.ts` grows from 27,585 bytes and stays under the 30,000 that would oblige a sister document; the margin is stated rather than assumed, because #376 asked for that number and ADR-084 already spent part of it. Reasoning that would have pushed it further lives here, which is what this record is for.
