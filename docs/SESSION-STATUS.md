## What a live edit costs today

- `replace(next)` is for topology. It validates a whole `TrackDefinition`, stages a replacement Track, rebuilds the graph, and rolls back transactionally when refused.
- One binding of an already-bound plugin is editable on its own, and it costs one candidate build, one edge delta and one flush, because a binding adds, removes or redirects a `GraphEdge` and there is no cheaper path for that category. `setRequire(plugin, slot, source, memberKey?)` and `removeRequire(plugin, slot, memberKey?)` rewrite only that plugin's `requires` section, leave its values untouched, and return `void`, because the return type carries the tier: structural replaced the graph, the value tier returns the `PatchBatch` of its one invalidate. `memberKey` addresses one entry of a dict-valued slot by the key it was authored under, so two entries of one slot stay two edges. Removing the last binding leaves the section absent rather than empty, and a one-entry dict does not collapse to the scalar shape.
- What it does not cost any more is the timeline build. A binding edit changes no compiled property, because the flattened record the interpolator and the percent map receive carries the `values` section and nothing else, and the plugin it names is already in the chain by precondition, so `compilePercentKeyframes` and a fresh `Track` are declined while the resolve is still paid. See the predicate below.
- Its order is the contract, and both verbs share one owner of it. Staleness first, through the resolver every member of the handle reads. Then `keyframe-group-unbound` for a plugin this node authors no group for, which is `setKeyframeGroup`'s job and a different question from anything the registry answers. Then the edit, where a slot the caller named is checked against this surface's one reservation and the pure editor that knows the group layout runs, refusing `keyframe-require-shape` in either direction rather than silently dropping an edge the caller never named. Then the redundant edit, by identity, so binding a slot to the source it already reads costs no rebuild, no recompile and no flush. Then the commit.
- A whole plugin group is editable in place, at the same price, because it is one replacement too. `setKeyframeGroup(plugin, group)` writes the binding wholesale, values and `requires` together, whether or not the node authored one, because a group holding only half its data may be transiently invalid. `removeKeyframeGroup(plugin)` drops the group and every edge its `requires` derived in one commit, values included, because what is removed is the group rather than a section of it. Their order is `#editGroup`'s: staleness, then `keyframe-entry-shape` for a name this node authors as an ordinary property, then the pure edit, which refuses `keyframe-group-shape` for a group naming no reserved section rather than committing a husk, then the redundant edit by identity, then the commit. An absent record reads as one frozen empty one, so originating on a track that authors nothing needs no branch. Either verb moves a plugin's `values` or its place in the chain in the ordinary case, so either one usually pays the timeline build the binding verbs decline.
- One entry of a solver's goals slot has one verb. `setGoal(plugin, memberId, source)` and `removeGoal(plugin, memberId)` are `setRequire` and `removeRequire` with the slot fixed rather than named, which is the whole of what they buy: no second copy of the dict rule, and no way to reach the scalar spelling of that slot, which the loader refuses as `keyframes-targets-shape`. The binding pair refuses the slot by name and points at them. Whether a member id names a leaf of the chain, and whether both goal spellings are bound at once, are `resolveSolvers`' questions, answered over the candidate and rolled back by the commit.
- One property of a plugin group this node already authors is writable and removable on its own, and it is the value tier rather than a cheaper structural edit. `setKeyframe(plugin, key, value)` and `removeKeyframe(plugin, key)` answer with the `PatchBatch` of one invalidate and reach `replaceGraph` on no path, because a leaf carries no edge and the plugin it belongs to is in the chain already. Which of two paths a call takes is decided by the record: a key the group already authors is `setValues({ [key]: value })` with the group named, so the write is a mask or a per-key rebuild of the still-live timeline and the retained definition moves with it; a key it does not author yet cannot be masked, because nothing compiled it, so the authored record is edited, the candidate is validated and resolved, and the node is recompiled in place at the progress it already had. The leaf-kind crossing stays refused in both directions, `keyframe-key-animated` does not exist, and a plugin this node authors no group for is still `setKeyframeGroup`'s job. See [ADR-065](./ADR-065-authored-property-editing.md).
- An authored edit leaves behind no shape that is legal only because nothing refuses it. A dict that loses its last entry loses its slot, a section that loses its last slot is removed rather than left empty, a group that names no section loses its entry, and a record that holds nothing loses the `keyframes` key. One rule at four levels with one owner each, which is why C1's `withRequires` now reaches `removeGroup` rather than leaving `{ plugin: {} }` behind. See [ADR-063](./ADR-063-whole-group-and-goal-authoring.md).
- The recompile a structural edit pays is two things wearing one name, and only one of them is skippable. The resolve is the validation: `compileTrack` reuses a live entry and never asks the registry, so the staging seam is the only path on which the registry sees an already-compiled node's candidate, and an undeclared slot, an unclaimed leaf and an unknown plugin name are all refused there, with the registry's own rule id at the path the author wrote. It is now asked before any effect is applied, so a refused candidate stages nothing at all rather than being staged and rolled back, and the message a caller reads is unchanged. The timeline build is the expense, and it is declined when the whole compiled input provably did not move: the definition outside its authored record, the flattened record, the plugin chain by content and in order, the prepared contribution and the declared internal keys. `domain/authoring/recompile.ts` is the one owner of that comparison. See [ADR-062](./ADR-062-candidate-key-ownership.md).
- One recipe is one transaction. `edit(recipe)` opens one, hands the recipe a narrowed `SchemaTransaction`, and commits what it staged exactly once, so `n` authored ops across `m` tracks cost one candidate build, one graph replacement, one `ObservationState` commit and one flush. Reads inside it resolve against the staged pair, a handle issued inside it is live for the rest of the recipe and never live after an abort, and the recipe's own return value is the caller's. A recipe that staged nothing commits nothing, answered by identity on the pair rather than by a dirty flag. A recipe inside a recipe is `schema-transaction-nested`, and a verb that applies immediately is `schema-transaction-immediate`, named at the verb: both in-place tiers, plus `mount`, `unmount`, `seek`, `invalidate` and `signal`. `mount`, `seek`, `subscribe` and `dispose` are absent from the transaction interface, and that absence never refused anything, because a recipe closes over the handle `edit` was called on.
- Every capability handle has one shape and one failure family. `Handle` carries `id`, `live` and `definition`; `live` never throws, on either side of any invalidation and on a disposed project, and every other member refuses with a named error under one abstract `StaleHandleError`. A caller that does not care which kind of handle went stale catches the base; one that does branches on `ruleId`. The resolvers `track` and `motion` refuse an id the project never had, and `tryTrack` and `tryMotion` answer `undefined` instead, so an upsert is two lines with the branch at the call site rather than one verb whose cost depends on whether the node exists.
- A Motion's trigger and its stagger are editable in place, and that edit is tier 0: it reaches no node and no edge, so it goes through two hooks of its own rather than through `#commit`, and it tears down none of the tracks the motion owns. Changing a trigger no longer means destroy plus recreate, which tore down every node under it. `setTrigger` validates through the same `validateMotionTrigger` that `addMotion` asks and refuses before any teardown, asks the driver layer nothing when the trigger is the one already installed, reports that layer's failure verbatim with the retained definition unmoved, and keeps the playhead because the port is swapped in place rather than the Motion rebuilt. `setStagger` clears by omission, leaves no `stagger` key behind when it does, and re-seeds every track's effective progress synchronously, exactly as `addTrack` and `replaceTrack` already re-seed.
- Every structural change runs through one `#commit(plan)`. A plan carries the maps the graph is asked to accept, the effects that must be in place before it is asked, and the steps that settle once it accepted. Effects are reverted in apply order rather than reverse, because the displaced compiled Track has to be republished before the Motion entry is restored, and an effect counts as applied only once its call returned, so a hook that refused before writing anything is not restored. A commit adopts the accepted pair rather than copying it into the maps this runtime holds, so the committed graph and the retained definitions cannot drift and a commit that moved one entry writes one entry: the half it did not move is absent from the plan and the half it did move is a map one of the two staging accessors made for it. A recipe pays one copy of that pair rather than one per op, taken by the first op that stages anything, which is what keeps a recipe that staged nothing answered by identity rather than by a dirty flag. The price of adopting a builder's map is that the retained fields are no longer `readonly` and no builder may keep what it handed over. A replacement whose timeline build was declined applies one effect fewer, and nothing else about the transaction moves.
- A structural commit ends at one flush, seeded with the nodes it touched and run after the settle steps, because one of those steps is the mount. An add, a replacement and every authored edit seed the edited node; a motion add or destroy and a removal seed nothing, because the first two derive no node at all and a removal's node is gone with nothing left depending on it. An empty seed set is not a cheap flush -- it still opens a batch, notifies every batch subscriber and moves the sequence -- so a commit with nothing to publish does not call `invalidate` at all. `addObserve` on a manual clock with no tick publishes now, and a new node whose sources have not published yet lands on `blocked` with a pending diagnostic rather than on nothing.
- So a runtime add publishes at rest and `Engine.load()` does not: a loaded project publishes nothing until something ticks. That asymmetry is real and `T-1` owns it, restated as parity of the progression a driver produced rather than of the batches it arrived in. Whether load should seed a flush too is unasked and unanswered; it has no members yet when it would.
- The compiled map is the one owner of a `Track`, and every seam that reads one resolves it per call: ordinary composition, the publisher's `MemberState` for a solver member, the progress hook, and `Motion`. Nothing captures an instance, because an escalation replaces an entry without touching the graph, and the publisher caches one node per graph node: a captured Track was the disposed one from that commit on, and a solver was the one reader that had captured one.
- `replaceGraph` still clears the publisher node cache, and that clear is residency rather than staleness. The map is keyed by the graph node object and holds it strongly, so without it every node a rebuild replaced would be retained for the life of the runtime. It is not what makes a recompile visible, and deleting it on that reading would trade a correctness fix for a leak.
- A flush costs the nodes it touches rather than the size of the graph. Graph shape is read, never derived: `finalizeGraph` freezes `nodeById` and `dependents` onto the `GraphIR` once per graph, and the publisher's affected walk and upstream walk both start from the seeds, so a steady-state tick allocates nothing for graph shape. Reverse topology is total, so a node nothing reads carries an empty list rather than no entry, and it names both kinds of reader, because a solver reads its members through `solves` and no edge points that way.
- The runtime does not build the thing it hands the publisher either. One `PublisherSnapshot` is derived per graph and read on every flush after that, keyed on the `GraphIR` identity and on a membership revision, because which nodes are mounted is the one part of it that moves while the graph stands still. The member set inside it is a copy for exactly that reason: a frozen snapshot aliasing the live one would answer differently without its key having moved, and a memo keyed on the graph alone would look correct until something mounted.
- `overrideValues(values)` is revertible and leaves the retained definition alone. `setValues(values)` is sticky and rewrites it, so `handle.definition` and the live composition cannot disagree. Both stage no Track for a static write, rebuild no graph on either path, and return the `PatchBatch` of their one `invalidate`.
- Either member takes an animated key. A static key is masked over the interpolated state; an animated key has its tweens replaced on the still-live timeline against a base the interpolator retained, at the same progress. An interpolator with no `patchKeys` escalates to a recompile through `stageTrack` and one re-seek, and publishes the same values, so the two backends are observably identical. That escalation reaches the staging seam directly and is not the structural path, so the predicate above never sees it.
- A write is replaced wholesale rather than accumulated. An empty record is the clear, back to the authored values or to whatever the last `setValues` wrote, and a real `replace()` drops it by construction. Every structural edit drops it too, for the same reason: they route through `#replaceTrack`, which retains a fresh entry with no overlay.
- An animated write validates the rewritten definition through `validateTrackDefinition` before anything mutates, because an authored stop list is definition-shaped input. A static-only write skips that and costs exactly what it did before.
- Three refusals and no fourth. `LiveValueKeyError`, rule id `live-value-key`: `unknown` for a key the track does not author, `kind` for a leaf shape change, and `prepared` for a key a plugin already decided the value of.
- `seek(nodeId, progress)` is leaf-level scrubbing. On a driver-backed Motion the next driver emission overwrites a seeked value.
- Owner-based `adopt` and `destroyAdopted` remain available for existing consumers. New consumer code uses `addTrack` and `TrackHandle`. `adopt` returns `{ id, track }` and keeps that field name: it is a value rather than a live read, so the handle rename does not reach it.

## Working constraints

- `format:check` runs before `npm test` inside `quality`, so a formatting slip means the suite never ran and the run proves nothing. Prettier is configured `printWidth: 100`, `singleQuote: false`, `trailingComma: "all"`, `proseWrap: "preserve"`.
- No Markdown tables in new prose, in test comments, or in an ADR. Anything that wants to be a table becomes a bullet list or prose. Prettier formats fenced `ts` blocks too, so pseudo-code goes in a `text` block. It normalizes asterisk-delimited emphasis in Markdown to underscores as well, so prose that wants emphasis is rewritten without it.
- Formatting never shares a commit with behavior.
- Six checks gate a merge: `quality`, `integration`, `boundaries`, `build`, `end-to-end`, and the advisory `performance`. Squash merge once they are green.
- A failed or timed-out `CI` or `Recovery audit` run archives to the `ci-logs` branch at `logs/<run-id>/`, with `README.md`, `run.json` and `failed-jobs.log`. Cite the Actions URL as primary and read the archive for durable failing-first evidence. `archive-ci-logs.yml` is deliberately not branch-filtered, so a `feat/**` head ref needs nothing dispatched by hand; manual `workflow_dispatch` with a `run_id` stays available for a run the `if:` gate skipped.
- A test file naming a member that does not exist yet fails `typecheck` and stops `quality` before `npm test`. Declare the not-yet-existing seam locally in the red file and cast, then delete that declaration in the commit that lands the source. `StaleSeam`, `ComposeSeam`, the `LV-` locals, 7a's `ReverseTopology`, B2's `TierZeroEdits`, C1's `RequireEdits`, C2's `GroupEdits` and C3's `ResolveSeam` are the precedent. Where the seam is a hook the real options declare, the shipped file derives its type from that option rather than restating it, so a hook whose shape drifts fails `typecheck` instead of a case. A case that asserts a member is **gone** needs none of that: `"name" in object` typechecks before and after the deletion, which is what `RA-16` uses, and `Object.keys` answering a question about a spelling is the same, which is what `RA-27` uses. A member of an interface has no run-time shape to ask about at all, so `RA-78` reads the declaration as text instead, which typechecks on both sides and fails on an assertion rather than on a compile. Neither is needed for a case whose subject is identity rather than shape: `RA-23` compares the objects two flushes were handed, which typechecks against the interface that already exists.
- The interface and the handle factory are one push, not two. C2 declared four members on `TrackHandle` in the commit that landed the pure editors and built them onto the frozen handle in the next one, which cost a whole `CI` run to `TS2739` on the object literal and proved nothing. A member added to a public interface is finished at its implementor before the push, the same rule a rename already follows.
- `CI` triggers on `pull_request`, so several commits pushed together produce one run on the head rather than one per commit. Evidence that has to be cited by run id therefore ships in its own push, and an equivalence slice whose evidence must be green on both sides of a refactor ships that evidence as its own pull request. A3 is the first slice cut that way from the start: the evidence commit was pushed, the pull request opened on it, and the source pushed after, which is what A1's retro asked for. 7a, 7c, B1, B2, C1, C2, C3 and F are cut the same way.
- A source push that lands one half of a slice earns its own `CI` run, and that run is not evidence of anything. C3's middle run landed the pure comparator with nothing calling it yet, so the same two assertions failed for the same reason; it is cited in the pull request body as not evidence, exactly as B1's `typecheck` failure and C2's `TS2739` are. F has one of the same shape: the commit that deleted the declaration landed before the commit that refused the field, so `RA-78` went green while `RA-77` still failed.

## Guardrails

- One owner per state transition, and one owner per normalization.
- One question, one mechanism. Where two mechanisms answer one question, the weaker one is deleted rather than documented as discouraged. A solver's goals slot is the case C2 closed: `setRequire` could reach it in two spellings, one of which the loader refuses and one of which is the right shape through the wrong verb, so the slot is reserved by name and `setGoal` is the owner.
- One condition has one failure contract. Where half a surface refuses loudly and half returns silently, the silence is deleted and a non-throwing probe is added for the callers whose second call is expected rather than mistaken. A nullable return is the same silence with a value nobody checks.
- A contract shared by two implementors is stated once, in the thing they both extend. A handle's asymmetry between a probe that never throws and members that always do is the case it was written for: declared per implementor it is two authors for one rule, and the read-back member drifts into two names for one fact the first time a second handle is added.
- No compatibility flags, facades, placeholder tests, renderer imports, or core GSAP imports.
- A `set` verb over two operations is one name too few, unless the two are the same operation. `setMotion` and `setTrack` were cut because create assigns an id and mounts while replace refuses a definition whose id would move the node; `setKeyframeGroup` is an upsert because a group carries no id, no token and no mount, so both directions cost one rebuild and refuse the same things. The test is whether the cost and the refusal set depend on what was there before, not whether the name reads well, and the edit is wholesale rather than merged for the same reason.
- A rename with no alias is finished at every reader before the push that lands it, and `typecheck` is the gate that proves it, not review. B1 renamed one exported member and missed seven call sites across two test files, which arrived as four assertion failures in one job and seven `TS2339`s in another: one cause, two red jobs, and neither of them evidence of anything. It also missed both guide documents, which no gate reads at all, so "every reader" means every reader rather than every reader a job can see.
- Every behavioral slice starts with failing-first evidence, and failing-first means failing assertions. A run that failed `typecheck` or `format:check` ran no test at all, so it is a broken file rather than evidence.
- A refusal a slice introduces has a failing case before it, on the same rule. C1's `keyframe-require-shape` is the one that earned this: a decision to refuse rather than to accept silently is a behaviour, so `RA-47` landed with the red half rather than beside the source. C2's three refusals ship the same way, and so does F's one.
- How many cases a red run may turn red is a property of the slice, and it is reported rather than engineered. A capability slice turns its whole block red, because nothing answered before. An optimisation cannot: before it lands, the expensive path always runs, so every case asserting that the expensive path ran is green against the old behaviour by construction, and only a case counting the skip or a refusal the slice moved can fail. C3 turned two of five red for exactly that reason, and the three that stayed green are labelled in the pull request body as green on purpose. Padding a red count by asserting less in the cases that could not fail is the failure mode this rule exists to refuse.
- A green case is only evidence of what it would fail without. A test whose assertions survive the fix being reverted, or its twenty inputs collapsing to one, is rewritten rather than counted. Where a consumer is meant to stop deriving a fact and start reading it, the case that proves it hands over a shape only the new reader can see, and says in the file that it is a lie detector rather than a shape any producer can make. Where a slice replaces a derivation with a memo, the case asserts both halves of the key, because a memo that never rebuilds and a memo that always does are both green against half of it. A case whose whole subject is a refusal asserts the accepting direction too, in the same rig, because a primitive that refuses everything is green against the refusal alone: `RA-46`, `RA-51`, `RA-55`, `RA-60` and `RA-77` are that shape. A scan asserts that it found the thing it is scanning, because a scan that matched nothing answers "absent" for every spelling: that is `RA-78`'s first assertion and the evidence-id gate's own second case.
- A rig that measures where an answer came from removes every other layer that could have given it. C3's is the case: its staging seam refuses nothing at all, so the refusal `RA-60` reads can only be the resolve's, and deleting the resolve is a committed graph rather than a greener test. A rig that copied the real seam would have been green either way.
- An optimisation is proved by an oracle as well as by a counter. A skipped build is only correct if the node still publishes what the same document publishes when it is authored that way and loaded fresh, and a call count cannot see a stale composer, a stale flattened record or a stale prepared contribution. `RA-59` is that oracle, and it asserts the built direction in the same rig so it cannot be green against a predicate that never skips.
- A case that goes red because a slice moved the point at which something happens is read before it is rewritten. Where the assertion was reading the right fact in the wrong place, the read moves and gains the assertion that the old place is now empty, because published-early and published-twice look the same otherwise. Where the case owned the timing itself, the invariant is restated and the difference it no longer carries is asserted somewhere, in one place. Neither is a licence to loosen an assertion to reach green.
- Docs, public types, tests, and status move together. A cited evidence case id names exactly one test in the suite.
- A public error type is declared where the package entry may name it. A caller cannot `instanceof` a type it cannot name, and the declaration-surface gate refuses a `runtime/` or `graph/` module in the entry's declaration closure, so a shared no-behavior layer is where such a type lives while ownership stays put. The same rule reaches a parameter type: a member the entry exposes is unusable if its argument type cannot be imported.
- An optional port member is a segregation decision, not a convenience. It is optional when an implementation genuinely cannot honor it, and the caller's answer has to be total on success and on failure, or the two implementations are not substitutable.
- An optional hook and a total answer are two separate questions. A supplier may be absent, and the answer it gives when present may still be required to be total: a provider that could answer "this node has nothing" made the publisher report a missing seam instead of a missing node, so the provider is optional and its return is not. `resolveKeyframes` is the same shape: absent when no registry was injected, and total when one was.
- Two hooks rather than one where which hook was asked is itself part of the claim. A field no driver reads, routed through the hook that owns the driver, disposes a live host subscription for nothing, and one hook carrying both fields cannot be told apart from a correct edit by any counter.
- A boolean return that means two incompatible things is one defect. Where a member can answer both "your input was bad" and "I cannot do this cheaply", the first is moved to the owner that can refuse before anything mutates and the second is all the boolean keeps.
- An authored section is reserved by name rather than inferred from shape. A wrapper that exists only to hold one value is deleted, and the thing it held becomes the value.
- A field with no consumer is removed and then refused, never left declared or silently ignored. A union member is held to the same rule, and so is a method: `clearPublisherCache()` existed for a staleness that had one real cause, had zero callers for as long as it existed, and is deleted rather than kept as the escape hatch for the next one. An edit is held to it too: a group naming no section, a section holding no slot and a record holding no key are all fields a reader ignores, so the thing that emptied is removed rather than committed. `ProjectDefinition.templates` is the field the rule was written for and the last one it had left to reach: it is deleted and refused as `project-templates-unsupported`, by its key rather than by the value at it, because an authored `undefined` is still a key a reader would ignore and a value check would let the field back in through a spread of an older document.
- A derived fact is derived once, by the layer that already walks the thing it is derived from. Where two consumers each rebuilt it, the one that is not the owner reads it instead, and a map that answers per id is total rather than sparse, because a missing key and an empty entry are the same answer to a consumer that spells `?? []` and only one of them makes the map's shape depend on the input.
- An authoring primitive does not authorize its own edit. It builds a candidate and the owners that already judge a whole authored record judge that candidate, because a per-primitive check is a second owner of ownership that can disagree with the loader in exactly the case nobody tests. What stays the primitive's own is only what no other layer can see: whether the thing it was asked to edit exists on this node at all, whether the edit would cross a shape the caller did not name, and which verb owns the slot or entry it was handed.
- An optimisation that removes a step is read for what that step also owned. C1 is the case: a recompile that looks like pure expense on a requires-only edit is the only place a plugin registry ever sees an already-compiled node's candidate record, because `compileTrack` reuses a live entry and returns early. Skipping it would have deleted a validator rather than a cost, and shipped an undeclared slot carrying a real edge into a consumer that does not exist. So C3's predicate skips the timeline build and never the resolve.
- An optimisation is scoped by everything the thing it skips is built from. C3 is the case: the predicate was named as one field of the resolved answer, and a compiled `Track` reads five things plus its whole definition, so the comparison covers all of them and answers "changed" for anything it cannot prove. A predicate narrower than its subject is a skip that is right until an unrelated field moves.
- An answer needed on both sides of an edit is recomputed unless its owner is the one keeping it. Retaining the resolved chain beside the compiled map would have been a cache keyed on a registry's contents, written and restored by four call sites staying in step; resolving both records instead costs the cheap half of a compile and cannot drift.
- A handle answers about live state rather than about the entry it was built from. A motion whose retained definition carries an empty `tracks` list by construction would report owning nothing while owning three, so the projection reads the same owner the committed snapshot reads and the count in a refusal cannot disagree with the list a handle shows.
- A rule answers for the scope that owns the thing it refuses. A rule that reserves an authored key across the whole registry is the same defect wearing the opposite shape, and a slot reserved on the plugin that happens to own it rather than on the slot itself is the same mistake one level down.
- A misconfiguration with no symptom is refused by name at load time. A rig that holds a broken pose silently is worse than one that fails to load.
- A cache is keyed on everything its answer depends on. Where widening a key would reproduce another owner's key, the cache is deleted instead. Its residency is the owner's own question too: a cache that only ever grows is answered inside the layer that holds it rather than by three callers that have to stay in step. And a line that maintains a cache is read for what it is actually for: the publisher cache's clear looked like a staleness fix and was residency, so the staleness was fixed at the closure and the clear stayed.
- A cached value that aliases a live collection is not keyed on it at all. Where a memo has to carry something mutable, it carries a copy and the key carries a revision the one owner of that collection moves, because the alternative answers differently without the key having moved, and it hides the missing key behind an answer that happens to be right.
- A helper that already exists and already does the arithmetic is called, not copied.
- A gate reads code, never prose. A scan for a retired form is narrowed to what that form can be written in; product text is not reworded to satisfy an assertion. `RA-78` reads a type declaration for the same reason: the declaration is code, and the sentence in the guide that used to promise the feature is not what the gate is asking about.
- A mechanical edit is read for the prose it moved as well as for the code. E's extraction of `#boundGroup` inserted it between `#editRequire` and the docblock that documents `#editRequire`'s order, which left one comment owning the wrong member and the new member owning none. A docblock is part of the thing it sits above, so a script that moves a member moves that too or leaves the member where it is, and the review reads the boundaries of the move rather than the diff of the body.
- A debt list is a measurement, not a ledger. The guide-debt list in this file was appended to per slice and never re-read, so four of its seven claims described work a later slice had already done, and a reader trusting it would have rewritten documentation that was already correct. It is rewritten from the files rather than from itself.
- A refactor that only exists to unblock a later slice still ships alone, with its own equivalence evidence. A feature slice is held to it too: B was cut in two because the handle base and a live driver edit are two invariants with two refusal sets, and the first does not need the second to be provable. C3 was held to it as well, which is why the recompile predicate is not inside C2's four verbs. D is the one exception the rule always allowed rather than a break in it: a refactor whose correctness is indistinguishable from the behaviour it replaces until a new capability exists has no evidence of its own to ship with, so it ships with the first case that can tell the two apart and that case is named in the body.
- A verb that applies immediately is refused by name inside a transaction rather than deferred into it. A settle step cannot refuse, so deferring one would move its failure to after the graph committed and after the retained definition moved, and one condition would end up with two failure contracts. Tier 0 and tier 2 are both refused inside a recipe for that one reason, named at the verb so the message tells a caller which call to move out, and so are the five verbs that publish or mount without belonging to either tier.
- A narrowed surface handed to a callback is not a fence, so an invariant enforced by narrowing is enforced nowhere. The callback closes over the thing it was narrowed from, which is how `seek`, `mount`, `unmount`, `invalidate` and `signal` went on applying immediately inside a recipe while both in-place tiers refused: half a condition loud and half of it silent, out of a docblock that described an interface and was read as describing the run. A refusal goes at every verb that has the shape, and a docblock about a surface says which surface it is about.
- A default that exists to keep every prior rig byte-identical is proved by the prior rigs, not by a new test. C3's absent `resolveKeyframes` is the case: every registry-free rig in C1's and C2's files is what proves a replacement still builds when nothing was injected.
- An audit's claim about callers is a measurement, not a premise. A plan's claim about the code is the same: a finding verified against an older `main` is re-verified before it is cited, because a stale finding is how a decision gets made for a reason that no longer holds. A plan's own conclusion is held to it too: plan v2 of issue #222 verified finding 4 correctly and drew the wrong conclusion from it, which is how a capability was priced as impossible instead of being priced. A plan's prescription is held to it as well: A2 was planned to end at one unconditional `invalidate`, and an empty seed set turned out to cost a whole batch, so the plan was corrected in the slice rather than followed into it. 7b is the third: its two halves were planned as one slice, and reading them found one to be a correctness fix and the other a leak, so the first shipped inside A3 and the second was refused. C1 is the fourth, and the largest: the plan's own optimisation would have deleted the only validator on the path it optimised. C2 is the fifth, and the smallest: the plan called `setKeyframeGroup` an originate-only verb, and reading it found originate and replace to be one operation, so the slice shipped one upsert rather than two names. C3 is the sixth: the plan named the predicate as one field of the resolved answer, and reading it found that field to be one of five things a compiled `Track` is built from, so the comparison covers the whole compiled input and `RA-61` is the case the plan read literally would have failed.
- A claim about a slice's own evidence is a measurement too. C3's pull request body was written before its red run and predicted four red cases; the run turned two red, because the other three assert that a build happened and the pre-slice behaviour always built. The body was corrected from the run rather than the run read to fit the body, and the rule that generalises it is two bullets up in the failing-first group.
