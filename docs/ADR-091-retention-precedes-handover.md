# ADR-091: Retention precedes handover, is total across phases, and keeps the sink's own failure

**Status:** Accepted, 2026-09-16

**Context.** Three findings from the second quality pass over the runtime publication seam, read at `842bf74e9699eff6047db4042d392bc1dfab5bff`: [#415](https://github.com/chahyasantoso/motion5/issues/415), [#409](https://github.com/chahyasantoso/motion5/issues/409) and [#410](https://github.com/chahyasantoso/motion5/issues/410). They are one question read three ways, which is why they are answered together and not merged: what does a runtime retain, and when does it hand anything over. ADR-088 answered both halves in one act twice, in decision five and in decision six, and each time only one half needed the answer it got. All three findings read `GraphRuntime.#report` and `lastFlushError` from a different angle, and #415 says the thing that decides the shape of this record: a single rewrite of that member can satisfy or break the other two.

**Decision one. Retention precedes the handover, and the boundary owns that ordering.** [#415](https://github.com/chahyasantoso/motion5/issues/415). `reportDiagnostic` takes a `DiagnosticRetention` and calls `retain` before it touches `sink`. The defect was an ordering, not a missing feature: `#report` assigned `#lastFlushError` from the boundary's return value, so a sink that re-entered the runtime and caused a second report had its newer diagnostic filed by the nested call and then overwritten by the older outer one when that call unwound. `lastFlushError` is the runtime's public answer for what went wrong, and the failure it lost was always the newer one. Nothing documented forbids a host from re-entering, and [#393](https://github.com/chahyasantoso/motion5/issues/393) exists because a handler that retires the runtime reentrantly is a real host. **Refined by [ADR-094](./ADR-094-one-closed-value-per-runtime-decision.md), 2026-09-18.** The sentence naming `DiagnosticRetention` describes a type the tree no longer has: the boundary is `report.ts`'s and it takes a `RetainTrace` updater over one `ReportTrace`, so the read, the decision and the write happen inside the boundary rather than through two slots the caller owns. The ordering this record decided is unchanged, and it is the reason the shape moved: retention still precedes the handover.

ADR-088's decision five already claimed this ordering in prose. So this is not a new decision so much as the code catching up with the record, and the reason it is recorded here rather than fixed quietly is that the fix moves an act across a module boundary: the caller keeps the storage and the boundary gains the rule.

**Decision two. `reportDiagnostic` answers nothing.** The return value was how the ordering went wrong, and once retention is an act inside the boundary, an answer beside the retained slot is a second way to obtain what the runtime knows. Two owners for one question is the defect this repository cares about most, so the function is `void` and the slots are the only answer. `#report` was its only caller in the tree, so no call site loses anything it used.

**Decision three. Retention is total across phases; delivery stays guarded.** [#409](https://github.com/chahyasantoso/motion5/issues/409). `#report` opened with `if (isDisposed(this.#phase)) return;`, which answered two questions with one branch, and only one of them had been decided. ADR-088's decision six is about what a host is handed, and a terminal runtime handing a host nothing is a defensible reading of ADR-083. Retention is a different question: recording what happened is observation rather than action, and a runtime that can no longer publish can still hold the reason it stopped. The guard now selects the sink, so `#lastFlushError` is written whatever the phase and a retired runtime withholds rather than discards.

The scenario is reachable rather than theoretical: caller-supplied composition disposes the runtime and then throws while a scheduled drain is publishing, `#drainScheduled` catches the failure and reports `flush-failure`, and the old guard dropped both the delivery and the record because the composition retired the runtime on the way out. It is latent in the sense that nothing in the tree reads `lastFlushError` after disposal, which is why the existing case asserted the loss as if it were the intent. Whether delivery after disposal is wanted is left undecided here, deliberately: it should be decided on its own rather than inherited from a guard that was answering something else.

**Decision four. A sink's own failure is retained in its own slot, and handed to nothing.** [#410](https://github.com/chahyasantoso/motion5/issues/410), and the issue's own preference. [#400](https://github.com/chahyasantoso/motion5/issues/400) was right that a host must not reroute a runtime failure from a position the publication boundary cannot see, and containing the throw is the whole of it. Losing the throw is the half worth revisiting: the exception was not rethrown, not chained, not retained and not counted, so a sink that failed for an ordinary programming error left no trace anywhere while the operation that reported through it appeared to have completed normally. The exception now becomes its own diagnostic under `diagnostic-sink-failure`, named for the report it failed to carry, retained in `lastSinkError`, and handed to nothing. ADR-088's argument survives intact, because it rules out delivery through `onFlushError` and never required losing the failure.

A distinct hook is refused, for the reason the issue gives: a hook is a second sink and therefore a second thing that can throw, and the boundary would then owe a boundary. A slot is read when a host asks and cannot fail while the runtime is unwinding. **Refined by [ADR-096](./ADR-096-a-failure-is-named-for-the-question-it-answers.md), 2026-09-18.** Which handover failure the slot holds when two of them happen inside one report was not decided here, and [#436](https://github.com/chahyasantoso/motion5/issues/436) is that an outer handover overwrote a newer nested one, so the slot named an older report's delivery while the retained report was the newer one. The slot names the handover of the newest report the trace retains; the retention ordering this record decided is unchanged and is what makes that decidable.

**Consequences.** `GraphRuntime` gains one public getter, `lastSinkError`, and one rule id, `diagnostic-sink-failure`, owned by `diagnostic-report.ts` because the handover is the only place that can know a sink threw. `GraphRuntime` remains unexported from `packages/core/src/index.ts`, so `DiagnosticRetention` and `reportDiagnostic` stay internal and the emitted declaration closure moves only by that getter. No existing rule id, diagnostic shape or public verb moves. `#report` gains no branch: it selects a sink and delegates, and the phase question it asks is the one it already asked. **Refined by [ADR-094](./ADR-094-one-closed-value-per-runtime-decision.md), 2026-09-18.** `diagnostic-report.ts` is deleted, so `report.ts` owns the handover and the `diagnostic-sink-failure` rule id for exactly the reason this paragraph gives, and `lastFlushError` and `lastSinkError` are both answered from one `ReportTrace` rather than from two independent slots. The sink selection is no longer a ternary at the boundary either: `reportSink` in `graph-runtime-state.ts` is the module that owns that union and therefore owns the switch over it. Both getters, the rule id and the public surface are unchanged.

One existing case changes its claim rather than its subject. `deferred-payload.test.ts` pinned a terminal runtime as carrying neither work nor a diagnostic, and the second half of that was the guard's accident rather than a decision, so it now reads an empty sink beside a retained `flush-failure`. `diagnostic-retention.test.ts` is the new evidence and both of its behavioural cases are red before this change: a reentrant sink that reports again, and a throwing sink whose own failure had nowhere to go. The reentrant case makes its second report through the clock consumer boundary, so the two diagnostics differ in rule id and in frame and the slot cannot pass by naming either one loosely.

**Alternatives refused.** Splitting the boundary into `buildDiagnostic` and `handOver` and letting `#report` assign between them: refused, because it hands the ordering back to the callers the boundary exists to relieve, and the boundary exists precisely because five callers should not each own a rule about the host. Keeping the return value alongside the retain callback: refused as two answers to one question. Delivering the sink's failure through a second hook: refused as a second throwable sink. Delivering it through `onFlushError`: refused as a loop, which ADR-088 already settled. Rethrowing the sink's failure: refused, because it would let a host reroute a runtime failure, which is the whole of #400. Making retention conditional on the phase and delivery unconditional: refused as the exact inversion of what the phase is able to say. Deciding delivery after disposal in this record: refused as a separate question that should not be inherited from a guard.
