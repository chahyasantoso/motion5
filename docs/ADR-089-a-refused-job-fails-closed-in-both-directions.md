# ADR-089: A refused job fails closed in both directions

**Status:** Accepted, 2026-09-16

**Context.** [Issue #402](https://github.com/chahyasantoso/motion5/issues/402), found by the quality pass over [#398](https://github.com/chahyasantoso/motion5/pull/398), and [issue #394](https://github.com/chahyasantoso/motion5/issues/394) beside it. ADR-086 decided that the `Scheduler` port states its own deferral rule and that `deferredScheduler` enforces it, and it recorded the mechanism as "the refusal leaves through `schedule`". That sentence is true only of a port that propagates the exception thrown out of the wrapped callback, and the population this guard exists for is ports that are out of contract. A port already breaking one rule cannot be assumed to keep another.

Two interleavings escaped, and both leave the runtime in a state it was told it was not in.

A port that runs the callback inline, catches the refusal and answers a handle made `schedule` return normally. `#scheduleDrain` stored that handle and answered `true`, so no `scheduler-failure` was reported and the deferral diagnostic told the caller a scheduled drain would publish the work. Nothing was ever going to run it, and the seeds sat pending until some later publication happened to carry them.

A port that accepts the callback and then throws made `schedule` fail, so the booking was released and the failure reported, and by then `scheduling` was back to `false`. If the port later invoked the callback it had retained, the wrapper saw `scheduling === false` and ran the job, draining against a runtime that had been told its booking failed. The permanent `refused` latch does not help in either case, because it is only read on entry to `schedule`.

**Decision one. The guard is fail-closed for the call in flight as well as for later ones.** Each wrapped callback carries its own liveness flag beside the shared latch. The flag is per call because the callback it invalidates is per call, and the latch stays shared because a port that has run one job inline has disqualified itself from every later one. A refused or failed callback is inert: invoked afterwards it returns without calling the job, so a retained callback cannot become a late drain.

**Decision two. A refused call is never answered with a handle.** When the inner port answers one after its callback has been refused, that handle is cancelled and the refusal is thrown. This is the first of the issue's two options, and the reason is the one it gives: the compliant path stays byte-identical and only the path that is already broken pays anything. Answering an inert handle of our own for every call was refused, because it would take away the port's real cancellation, which [#389](https://github.com/chahyasantoso/motion5/issues/389) made load-bearing when the booking became a claim about the scheduler rather than about the phase.

Cancelling is best-effort by construction: a port that cannot cancel the job it should never have run is out of contract a third time, and its failure must not replace the refusal this call reports. That is stated where it happens rather than left to a reader. **Refined by [ADR-096](./ADR-096-a-failure-is-named-for-the-question-it-answers.md), 2026-09-18.** The same sentence now holds for a port that swallows the refusal and then throws an error of its own, which [#436](https://github.com/chahyasantoso/motion5/issues/436) found undecided rather than decided: the refusal is the value that leaves and the port's error travels as its `cause`, so nothing the port supplied is dropped either. The per-call `ranInline` flag this record's amendment named is now the retained refusal itself, because one value answers both whether the callback ran inline and what it threw.

**Decision three. This is what closes [#394](https://github.com/chahyasantoso/motion5/issues/394), and it closes it at the port.** That issue reads the same defect from the runtime's side: a handle for a job that has already run is stale, and code holding it believes a drain is coming. Its three suggested answers were to make every scheduler asynchronous, to wrap synchronous completions so only valid handles are returned, or to document that such handles are unreliable. The first is not ours to promise about a host's port and the third is a comment rather than a fix. The second is this decision, taken one layer earlier: a synchronous port never reaches the runtime with a handle at all, because `schedule` refuses, and the runtime's existing boundary for a port that refuses work releases the booking, reports `scheduler-failure`, and leaves the seeds pending for the next publication. A stale drain handle is therefore unreachable rather than documented.

**Consequences.** No public surface moves and no rule id moves. The compliant path gains one closure variable and one comparison per scheduled job. One existing case changes its expectation rather than being weakened, and the change is the finding: `refuses every later call once a port has run one job inline` asserted that the swallowing port's first call did **not** throw, which is precisely the fail-open behaviour #402 names. It now asserts that the call is refused, that the handle it offered is cancelled, and that the latch still refuses every later call. Two new port-level cases cover the retained callback and the cancelled handle, and one runtime-level case covers the evidence #402 asks for: `scheduler-failure` reported, `pendingSeeds` intact, and a deferral diagnostic that does not claim a scheduled drain.

ADR-086's sentence about the refusal leaving through `schedule` is not deleted, because it is now true without a qualifier. What changes is that it is enforced rather than assumed.

**Alternatives refused.** Answering an inert handle for every call: refused above, it costs the port's own cancellation on the compliant path. Reading the latch inside the callback instead of a per-call flag: refused, because the latch is a statement about the port and the flag is a statement about one job, and a later compliant port composed over the same wrapper would inherit a refusal that was not about its job. Treating a swallowed refusal as success and reporting nothing: refused, because that is the current defect wearing a decision. Detecting a synchronous port by timing rather than by reentrancy: refused as unmeasurable and untestable.

**Amendment, 2026-09-16: the in-flight flag is per call too, and so is the question it answers.** [Issue #416](https://github.com/chahyasantoso/motion5/issues/416) reads decision one back and finds it half taken. The liveness flag became per call and `scheduling` did not, so it still answered whether a call had returned for every call at once. A nested `schedule` that began and ended inside an outer one lowered it in its own `finally`, and the outer callback, invoked before the outer `schedule` had returned, read a call that had returned and ran the job this port exists to refuse. Nothing was latched, because the latch is only set by a refusal that never happened, so the outer call also answered a handle for a job already spent and could recurse.

The answer is the first of the issue's two options, and it is decision one applied where decision one already pointed: `inFlight` is per call, and a callback reads the flag of the call it belongs to. A depth counter is refused for the reason the issue gives, which is the reason the latch is not read here either: refusal depends on whether this callback's own call has returned, not on how many unrelated calls are open.

One consequence is a behaviour change beyond the finding, and it is taken deliberately rather than left to be found by a third pass. The check after `schedule` returns read the shared latch, so a nested call's refusal cancelled an outer call's handle and threw for the outer call as well, even though the outer callback had never run. That is the same defect as #416 in the other direction: a claim about the port answering a question about one job. It reads `ranInline` now, so a compliant call is answered its port's real handle, which [#389](https://github.com/chahyasantoso/motion5/issues/389) made load-bearing, and the latch still refuses every later call on entry.

The evidence is two port-level cases, both red before the amendment. The first drives a nested compliant call and then the outer callback, and asserts the refusal, that the job did not run, and that the latch refuses the next call. The second drives a nested call that is itself refused and asserts that the outer call keeps its handle, that the job it names runs once the call has returned, and that cancelling it reaches the port.
