# ADR-077: Membership stays one verb per node

**Status:** Accepted, 2026-09-13

**Context.** Phase 5 of [issue #362](https://github.com/chahyasantoso/motion5/issues/362) was planned as a measurement rather than as an implementation, because `mount` publishes nothing under ADR-066, which makes the semantics of a loop and the semantics of a batch identical. The plan priced `mountAll` and `unmountAll` at two things: one membership revision bump and one `PublisherSnapshot` re-derivation instead of `n`, and all-or-nothing attempt semantics through the `collect` and `report` collector the teardown paths already use. It also said in advance what to do with the answer, which is why this record exists at all: if the saving is noise at realistic `n`, the verb is a facade over a `for` loop, the guardrails refuse facades, and the phase ends with a recorded measurement and no code. Both halves of that price were read against `runtime/graph-runtime.ts` and `runtime/project-runtime.ts` rather than assumed, and neither of them survives the reading.

**The measurement, and it is not the number the plan expected.** The re-derivation a batch would collapse does not happen once per mount, so there is no `n` to reduce to one. `GraphRuntime.#membersRevision` is the key `#snapshotFor` compares its memo against, not an invalidation that eagerly rebuilds anything, and `#snapshotFor` is reached from `flush` and from nowhere else. `attach` therefore costs one `Set.add` and one integer increment, `mount` adds one `Map.set` on `#instances` to that, and between them they compose no publisher node, freeze no snapshot, publish no patch and schedule no flush. So `n` mounts followed by one flush already derive exactly one snapshot, which is the best a batch verb could do, and the loop both demos run is exactly that shape. The saving is not noise at realistic `n`: it is zero at every `n`. What is left for the verb to remove is `n - 1` increments of a number nothing reads until the flush, while the verb still owes the same `n` `Set.add` and `n` `Map.set` calls, because it still mounts `n` nodes. A verb whose body is the loop it replaces, buying one integer per node, is the facade this project refuses by name.

**Decision.** No `mountAll` and no `unmountAll`. Membership stays one verb per node, and mounting a whole document stays a loop over the enumeration readers phase 2 landed. Phase 5 ends here, with the measurement recorded and no runtime code, which the plan named as a complete outcome rather than as a failure. The measurement is kept as four cases rather than as a number in prose, because a measurement in prose has no owner who can keep it true, and this project has already paid for that lesson in a file size that drifted 10,367 bytes with a green gate the whole way.

**Alternatives rejected.**

- A batch that mounts in a loop and moves the revision once. Rejected because nothing reads the revision between the mounts, so one bump and `n` bumps produce the same single derivation at the next flush. The optimal batch is observationally identical to the loop, which is the strongest form of this finding: there is no version of the verb that buys a publication, a derivation or a walk.
- The collector, which is the all-or-nothing half. Rejected on the two refusal sets rather than on taste. `unmount` returns on a node it does not hold, and `detach` and `PatchRegistry.remove` are idempotent, so `unmountAll` has no partial failure to collect at all and the contract would be written for a state it cannot reach. `mount` has exactly two per-id refusals, `Node "x" is already mounted.` and `Unknown graph node "x".`, and both are answered before the call by readers that already exist: the first by `mountedNodeIds()`, the second by `motionIds()`, `freeTrackIds()` and `MotionHandle.trackIds`, none of which can name a node the graph does not carry. Its other three refusals are properties of the call site rather than of the id list, being `ProjectRuntime is disposed.`, `schema-transaction-immediate` inside a recipe and `schema-commit-reentrant` inside a commit's own hook, so they refuse the whole loop at its first element or none of it.
- Rollback for the loop that does refuse partway. Rejected because the state it would undo is already readable: `mountedNodeIds()` is total and names exactly the prefix that mounted, so a caller resumes from the runtime's own answer. A collector reporting the same thing would be a second owner of a question a total reader answers, and its rollback would unmount work the caller asked for and can keep.
- The ergonomic argument. Rejected because phase 2 already spent it. With `motionIds()`, `freeTrackIds()` and `MotionHandle.trackIds`, mounting a document is a loop over the runtime's own answer rather than over a copy of its ids kept beside the definition, which is what both demos now do, and `docs/guide/api-reference.md` already says so. The plan made this point itself, and it is why phase 5 was ordered after phase 2 rather than before it.
- A dated revisit. Rejected for the reason ADR-076 refused a dated retirement: a date measures nothing, fails a build on a morning nobody picked, and is satisfied by editing the date. What reopens this decision is `RA-158` going red, which is precisely the condition under which the verb becomes worth pricing again.
- One more that is worth naming because phase 3 just deleted three members over it: `mount` answers with the instance it mounted, and a batch would either drop that answer or invent a collection shape for it. One answer with two spellings is the defect this issue has been subtracting.

**Consequences.** No public surface moves, no verb is added, no tier is added, and no failure contract is written, so there is nothing here for a consumer to migrate to or away from. No guide document changes either: `docs/guide/api-reference.md` already tells a consumer that mounting a whole document is a loop over the enumeration readers, and the absence of a member is not documented as a feature. `docs/LIVE-EDIT-COST.md` gains what a mount costs, because that document owns caller cost and the paragraph above is a caller-cost fact rather than a decision. The four cases below are green from the moment they land, and that is stated rather than dressed up as failing-first evidence: this slice changes no behaviour, so failing-first does not apply, and what the cases are is the tripwire under this decision rather than proof of a change. What each of them would fail without is named, because a green case is only evidence of what it would fail without.

**Evidence.** `RA-158` through `RA-161` in `packages/core/test/unit/runtime/membership-batch-refused.test.ts`.

- `RA-158` is the count the phase asked for, and it asserts both directions in one rig: four mounts before one flush hand the publisher one snapshot, and the same four mounts with a flush between them hand it four. Without the second half, a counter that can only ever answer one would be green against a publisher nobody called. It goes red if `mount` ever derives, publishes or schedules anything of its own, which is the condition that would make a batch verb worth pricing again.
- `RA-159` asserts `unmount` is total, and it asserts the accepting direction first: the verb does move a mounted node out, and it then no-ops on that same node, on a node this project never mounted, and on an id the graph does not carry. It goes red if a per-id refusal is ever added to `unmount`, which is the only thing that would give `unmountAll` a collector to own.
- `RA-160` mounts every id the three enumeration readers answer and asserts that none of them refuses, then asserts that both per-id refusals do fire on the ids those readers do not answer. It goes red if a reader ever answers an id the graph does not carry, which is the other way the per-id refusal could become reachable through the supported loop.
- `RA-161` runs a loop that refuses partway and asserts that `mountedNodeIds()` names exactly the prefix that mounted and that the loop resumes from that answer. It is the case a rollback would have to delete rather than the case a rollback would pass.

`packages/core/test/unit/runtime/publisher-snapshot-memo.test.ts` keeps owning the memo's keying, which is `RA-23` through `RA-26`, and this record does not restate it. That file owns whether the memo is keyed on everything its answer depends on; this one owns what a mount loop costs, and therefore what a batch over it would save.
