# ADR-077: Membership stays one verb per node

**Status:** Accepted, 2026-09-13

**Context.** Phase 5 of [issue #362](https://github.com/chahyasantoso/motion5/issues/362) planned as measurement, not implementation, because `mount` publishes nothing under ADR-066 → semantics of loop and batch identical. Plan priced `mountAll` and `unmountAll` at two things: one membership revision bump and one `PublisherSnapshot` re-derivation instead of `n`, and all-or-nothing attempt semantics through `collect` and `report` collector teardown paths already use. Also said in advance what to do with answer — why this record exists: if saving is noise at realistic `n`, verb is facade over `for` loop, guardrails refuse facades, phase ends with recorded measurement and no code. Both halves of price read against `runtime/graph-runtime.ts` and `runtime/project-runtime.ts`, not assumed; neither survives reading.

**The measurement, and it is not the number the plan expected.** Re-derivation a batch would collapse does not happen once per mount → no `n` to reduce to one. `GraphRuntime.#membersRevision` is key `#snapshotFor` compares its memo against, not invalidation that eagerly rebuilds anything; `#snapshotFor` reached from `flush` and nowhere else. `attach` costs one `Set.add` and one integer increment; `mount` adds one `Map.set` on `#instances`; between them they compose no publisher node, freeze no snapshot, publish no patch, schedule no flush. So `n` mounts then one flush already derive exactly one snapshot — best batch verb could do — and loop both demos run is that shape. Saving not noise at realistic `n`: zero at every `n`. Left for verb to remove: `n - 1` increments of number nothing reads until flush, while verb still owes same `n` `Set.add` and `n` `Map.set` calls, because it still mounts `n` nodes. Verb whose body is loop it replaces, buying one integer per node, is facade this project refuses by name.

**Decision.** No `mountAll`, no `unmountAll`. Membership stays one verb per node; mounting whole document stays loop over enumeration readers phase 2 landed. Phase 5 ends here, measurement recorded, no runtime code — plan named as complete outcome, not failure. Measurement kept as four cases, not number in prose: measurement in prose has no owner who can keep it true; project already paid that lesson in file size that drifted 10,367 bytes with green gate whole way.

**Alternatives rejected.**

- Batch that mounts in loop and moves revision once. Rejected: nothing reads revision between mounts → one bump and `n` bumps produce same single derivation at next flush. Optimal batch observationally identical to loop — strongest form of finding: no version of verb buys a publication, a derivation or a walk.
- The collector, the all-or-nothing half. Rejected on two refusal sets, not taste. `unmount` returns on node it does not hold; `detach` and `PatchRegistry.remove` idempotent → `unmountAll` has no partial failure to collect, contract would be written for state it cannot reach. `mount` has exactly two per-id refusals, `Node "x" is already mounted.` and `Unknown graph node "x".`, both answered before call by readers that already exist: first by `mountedNodeIds()`, second by `motionIds()`, `freeTrackIds()` and `MotionHandle.trackIds`, none of which can name node graph does not carry. Other three refusals are properties of call site, not id list — `ProjectRuntime is disposed.`, `schema-transaction-immediate` inside recipe, `schema-commit-reentrant` inside commit's own hook — so they refuse whole loop at first element or none of it.
- Rollback for loop that does refuse partway. Rejected: state it would undo already readable — `mountedNodeIds()` total, names exactly prefix that mounted → caller resumes from runtime's own answer. Collector reporting same thing would be second owner of question total reader answers; its rollback would unmount work caller asked for and can keep.
- The ergonomic argument. Rejected: phase 2 already spent it. With `motionIds()`, `freeTrackIds()` and `MotionHandle.trackIds`, mounting document is loop over runtime's own answer, not copy of its ids kept beside definition — what both demos now do; `docs/guide/api-reference.md` already says so. Plan made this point itself → phase 5 ordered after phase 2, not before.
- A dated revisit. Rejected for reason ADR-076 refused dated retirement: date measures nothing, fails build on morning nobody picked, satisfied by editing date. What reopens decision: `RA-158` going red — precisely condition under which verb becomes worth pricing again.
- One more worth naming, because phase 3 just deleted three members over it: `mount` answers with instance it mounted; batch would drop that answer or invent collection shape for it. One answer with two spellings is defect this issue has been subtracting.

**Consequences.** No public surface moves, no verb added, no tier added, no failure contract written → nothing for consumer to migrate to or away from. No guide document changes either: `docs/guide/api-reference.md` already tells consumer mounting whole document is loop over enumeration readers; absence of member not documented as feature. `docs/LIVE-EDIT-COST.md` gains what mount costs, because that document owns caller cost and paragraph above is caller-cost fact, not decision. Four cases below green from moment they land — stated, not dressed up as failing-first evidence: slice changes no behaviour → failing-first does not apply; cases are tripwire under decision, not proof of change. What each would fail without is named, because green case only evidence of what it would fail without.

**Evidence.** `RA-158` through `RA-161` in `packages/core/test/unit/runtime/membership-batch-refused.test.ts`.

- `RA-158` is count phase asked for; asserts both directions in one rig: four mounts before one flush hand publisher one snapshot, same four mounts with flush between them hand it four. Without second half, counter that can only answer one would be green against publisher nobody called. Goes red if `mount` ever derives, publishes or schedules anything of its own — condition that would make batch verb worth pricing again.
- `RA-159` asserts `unmount` total; accepting direction first: verb does move mounted node out, then no-ops on same node, on node project never mounted, and on id graph does not carry. Goes red if per-id refusal ever added to `unmount` — only thing that would give `unmountAll` collector to own.
- `RA-160` mounts every id three enumeration readers answer, asserts none refuses, then asserts both per-id refusals fire on ids those readers do not answer. Goes red if reader ever answers id graph does not carry — other way per-id refusal could become reachable through supported loop.
- `RA-161` runs loop that refuses partway, asserts `mountedNodeIds()` names exactly prefix that mounted and loop resumes from that answer. Case rollback would have to delete, not case rollback would pass.

`packages/core/test/unit/runtime/publisher-snapshot-memo.test.ts` keeps owning memo's keying — `RA-23` through `RA-26` — and this record does not restate it. That file owns whether memo keyed on everything its answer depends on; this one owns what mount loop costs, and therefore what batch over it would save.
