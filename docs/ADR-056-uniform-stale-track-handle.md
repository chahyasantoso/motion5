# ADR-056: A stale TrackHandle refuses uniformly, and `live` is the non-throwing question

**Status:** Accepted, 2026-08-29

**Context.** `ProjectRuntime.#handle` exposed a token-guarded `TrackHandle` with two public failure contracts for one condition. The `track` getter threw `TypeError: Track "<id>" is no longer live.` when its token was stale; `remove()`, `replace()`, `addObserve()` and `removeObserve()` returned silently. A stale mutator therefore reported success by doing nothing while the getter failed loudly, and the same comparison was copied into `#removeTrack`, `#replaceTrack`, `#replaceWithObservation` and the getter. `TrackHandle` itself was declared twice, in `runtime/project-runtime.ts` and in `engine.ts`, which is the defect shape the two private `readNumber` copies had before `plugins/frame.ts` existed.

**Decision.** All-throw. Every handle member routes through one resolver, `#liveEntry(id, token)`, which throws `StaleTrackHandleError` when the captured token is not current. The error extends `TypeError` and keeps the existing message verbatim, so a caller narrowing on `instanceof TypeError` or anchored on that string keeps matching; it carries a stable `ruleId` of `stale-track-handle`, which is what a caller branches on instead. A non-throwing `readonly live: boolean` probe answers the same question for callers whose second call is expected rather than mistaken, and `TrackHandle` is declared once and named by both consumers.

Ownership does not move. `ProjectRuntime` holds the tokens and the `TrackEntry` map, so it stays the only thing that answers whether a token is current, the only thing that builds a handle, and the only thing that throws. Nothing enters `Track`, graph code, an adapter, or a new lifecycle service, and there is no injection seam: token validation is pure in-memory policy against state this object already holds, so a port with exactly one implementation would buy a second owner for nothing.

The comparison has one owner and two readers. `#entryIfLive` performs it, `#liveEntry` is that plus the throw, and `live` reads the probe, so the refusal and the report cannot disagree about the same handle. `SH-7` pins it as a count: exactly one token comparison in the module, and no branch at all inside the handle factory.

**Alternatives rejected.** All-silent would have made the getter return `undefined` and given every caller a nullable to thread through for a condition that is a caller bug. A boolean return from each mutator is the same silence with a value nobody checks. A fifth copied guard beside the four existing ones was the shape the slice exists to delete.

**Consequences.** Four members now throw where they returned silently. The repository audit in issue #217 reported no caller relying on that silence and was wrong by one: `unified-mutation-surface.test.ts` called `remove()` twice across an ABA reuse and asserted the no-op. It is migrated to assert the refusal, and the guarantee it was really about, that a stale handle can never reach the node that reused its id, is unchanged.

A handle survives its own `replace()`. Replacement preserves node identity and therefore the token, which is what keeps a React consumer from seeing a node disappear and come back, so `live` stays `true` across it. The issue's wording said `live` is `false` after replace; that would have invalidated the handle every existing replacement case reuses, and the wording is corrected here rather than implemented.

On a disposed project `live` is `false` and never throws, but `remove()` reports the disposal rather than the staleness, because `#assertLive()` runs first. The runtime's own lifecycle outranks one handle's, and `if (handle.live) handle.remove()` is correct either way.

`StaleTrackHandleError` and `TrackHandle` are declared in `contract/track-handle.ts` rather than beside the runtime that owns the policy, and that is a gate rather than a preference. `public-declaration-surface` refuses any `runtime/` or `graph/` module reachable from the package entry's declaration closure, and a caller cannot `instanceof` an error it cannot name, so a public error type cannot live under `runtime/`. The dependency arrow is the one every layer already uses.

**Supersedes in part.** [ADR-026](./DECISIONS.md) said `remove` and `replace` are idempotent for stale handles. That is withdrawn. Its token and its ABA guarantee are unchanged; the idempotence is replaced by the refusal plus `live`.

**Evidence.** Cases `SH-1` through `SH-7`. Red run [33249505343](https://github.com/chahyasantoso/motion5/actions/runs/33249505343), archived at `logs/33249505343/` on `ci-logs`: `typecheck` and `format:check` both passed first, then `npm test` reported `6 failed | 734 passed`, one failed file out of 155, with integration, boundaries, build, end-to-end and performance all green. `SH-6` passed as a guard by design.

## Amendment, 2026-09-04: the lifecycle outranks the handle on every member that writes, not on the one that asked

The Consequences above state that rule and name one member as where it shows: `remove()` reports the disposal rather than the staleness, because `#assertLive()` runs first. It ran first there because `#removeTrack` asked it, and asking it was every caller's job. Seventeen of the eighteen writing members this runtime issues across `TrackHandle` and `MotionHandle` never asked, and `dispose()` empties the retained maps, so the token lookup misses and the resolver answers `StaleTrackHandleError` or `StaleMotionHandleError` instead. One condition with two public failure contracts, decided here and implemented once. Issue #298.

**The invariant.** Every handle member that writes reports `ProjectRuntime is disposed.`, and reports it before it asks whether the handle is stale.

**A read is unchanged, and the asymmetry is the decision rather than the amendment's scope.** Staleness on a write is misleading in a specific way: it says the thing the caller holds is out of date, which invites it to resolve a fresh handle and try again, and on a disposed runtime nothing it can do will work. Staleness on a read is true, because the entry the handle captured is gone, and it is the family this record exists to let a caller catch: changing `definition`, `requires` or `trackIds` would push a bare `Error` past every narrowing on `StaleHandleError` this record asked for. `live` still never throws, and `if (handle.live) handle.write()` is correct on either side of that line.

**The order has one owner, and it is a rung on the resolver ladder rather than a line per caller.** `#writableEntry` and `#writableMotion` ask `#assertLive` and then delegate to `#liveEntry` and `#liveMotion`, and `#writableId` delegates to `#writableMotion`. Every writing path resolves through one of the three, and every reading member keeps the resolver it already had, so the probe, the reader and the writer are three rungs with three readerships rather than three copies of one comparison. `#assertLive` is named twice in the class, which is the floor: two retained maps and two refusals, the same reason `#liveEntry` and `#liveMotion` were already two members. The count `SH-7` pins is untouched, because none of the three compares a token and none adds a branch to the handle factory.

**Refused: asking `#assertLive` inside `#liveEntry` and `#liveMotion`.** It is the cheapest change available, one owner and two lines, and it takes the read contract with it silently, for the reason above. `#entryIfLive`, `#motionIfLive` and `#liveOf` are refused harder: `live` reads them, and `live` may never throw.

**Refused: a line at the top of each affected path.** Seventeen copies of one ordering, and the eighteenth path added later is wrong by default. The defect being fixed is one condition with two failure contracts, so a fix whose correctness depends on every future author remembering a line is that same defect with a longer fuse. `#removeTrack`'s own `#assertLive()` is deleted for the same reason rather than left beside the resolver's, which is why `remove()` comes out of the slice behaviourally identical and with one owner fewer.

**Nothing else in the class moves, and that is measured rather than hoped.** `dispose()` clears `#open`, so a disposed runtime never has an open recipe and `#assertLive` and `#refuseInsideRecipe` can never both have something to say. Every per-verb order the class documents therefore survives, including ADR-061's amendment's contract for tier 0: liveness joins that sequence at the staleness step rather than as a step of its own. The one sequence in which both are lexically reachable is a `dispose()` inside a recipe followed by a handle write in the same recipe, and it answers the disposal, which is the answer ADR-064's amendment of the same date reached for `edit` itself.

**Evidence.** `SH-8` in `stale-track-handle.test.ts` and `RA-111` in `handle-base.test.ts`, one per handle family because there are two refusals and one file owns each surface. Each adds a writers-and-readers partition of the member record its own file already owns, `MEMBER_ARGUMENTS` and `MOTION_MEMBER_ARGUMENTS`, and asserts that the partition covers that record's keys exactly, so a member added to a handle later has to be classified rather than escaping this invariant by omission. Both collect per member rather than asserting one at a time, so a red run names every member that reports the wrong condition: `SH-8` was red on thirteen of fourteen and `RA-111` on all four. `remove` was green in `SH-8` on both sides, which is this record's own sentence being already true of exactly one member. The accepting direction is `SH-1` and `RA-32`, unchanged and green throughout, and it is not restated here: a handle made stale on a live runtime still refuses under `StaleHandleError` on every member.

**Consequences.** Seventeen members change which error they throw on a disposed runtime and none changes its signature, so no export, type or schema moves. A caller catching `StaleHandleError` around a write in order to swallow a disposal stops swallowing it, which is the behaviour this record already called correct for `remove()`. ADR-064's amendment of 2026-09-04 is corrected where it argued that two of `#apply`'s callers arrive through handle members answering staleness: they arrive through these resolvers now, and its conclusion holds for six callers rather than five. [LIVE-EDIT-COST.md](./LIVE-EDIT-COST.md) gains the caller-facing half, and [GUARDRAILS.md](./GUARDRAILS.md) the general rule, that a precondition outranking a lookup belongs to the resolver both readers share rather than to each caller of it.

## Second amendment, 2026-09-05: a read reports the staleness by decision, and the order it reports it in is a rung

The amendment above states the read half in one paragraph and measures it as an aside. `SH-8` and `RA-111` each assert that their file's reading members still answer under `StaleHandleError` after `dispose()`, but each does so inside a case whose subject is the writers, and the status file carried the read as the open question. Issue #300 asked which it is, for the whole `MotionHandle` read surface: `definition`, `trackIds`, `track` and `tryTrack`. It is a decision. This amendment ratifies it, gives it a case of its own, and removes the one thing about it that was never decided at all.

**The invariant.** After `dispose()`, every reading member of a `MotionHandle` refuses with `StaleMotionHandleError` carrying the captured motion id, and `tryTrack` refuses rather than answering `undefined`. `id` still answers, and `live` is still `false` and still never throws. On a live runtime nothing moves: `track()` refuses an unknown child by node id, `tryTrack()` answers `undefined`, and a handle made stale while the runtime lives refuses on all four.

**Three refusals are reachable from one lookup, and the precedence between them is what this amendment adds.** `handle.track(trackId)` can be wrong in three ways at once: the captured Motion may be gone, the child name may be ill-formed, and the child may not exist. The order is the Motion, then the name, then the existence, so a disposed runtime answers staleness without reading its argument and `qualifyMotionTrack`'s `TypeError` is reachable only on a live handle. That was already the behaviour and it was nobody's decision. It held because an argument is evaluated before the call it is an argument to, and both callbacks nested the resolve inside the qualification inside the delegate, so a slice rewriting either one of them would have changed half of this contract with the other half still green.

**`tryTrack` is the member the decision is really about.** It is the only one whose signature can absorb a refusal instead of reporting it, and `undefined` is not free of meaning there: it already says this child is absent from a live Motion. Answering it for a stale handle would collapse two facts a caller branches on differently into one value, which is the all-silent alternative this record rejected for `TrackHandle`, arriving through a probe rather than through a mutator. It is refused for the same reason and by the same argument.

**The order has one owner, and it is a rung rather than an expression per call site.** `#liveChildNode(motionId, token, trackId)` resolves the captured Motion through `#liveId` into a local, qualifies the child, and answers a node id; `track` and `tryTrack` are one call each. That is the shape the amendment above chose for the writes and it is chosen here for the same reason: one condition, one place that answers it, and an extension point for the day the answer changes rather than two call sites that both have to be remembered. The reading ladder is now four rungs with four readerships: `#motionIfLive`, which `live` reads and which may never throw; `#liveMotion`, which a read refuses through; `#liveId`, which is that plus the id; and this, which is that plus the child.

**Refused: `#assertLive` inside `#liveMotion` or `#motionIfLive`.** Unchanged from the amendment above, and issue #300's own ownership section reaches it independently. `live` reads that ladder and may never throw, and a guard placed there would take this read contract with it silently.

**Refused: a `#readableId` rung beside `#liveId`.** Symmetry with `#writableId` is the argument for it and it is a bad one. `#liveId` already is the read rung, and a second name for one member is the duplication this record's original decision exists to delete, spelled as a naming convention.

**Refused: a second member list for the readers.** `MOTION_READERS` already exists in `handle-base.test.ts`, and `RA-111` already asserts that it and `MOTION_WRITERS` partition `MOTION_MEMBER_ARGUMENTS` exactly. `RA-112` reads that same partition, so a member added to `MotionHandle` later still has to be classified rather than escaping this invariant by omission, and the two cases cannot drift about which members are reads.

**No standing rule is earned.** [GUARDRAILS.md](./GUARDRAILS.md) already carries the amendment above's rule, that a precondition outranking a lookup belongs to the resolver both readers share rather than to each caller of it. This slice applies that rule to an order between two lookups rather than restating it one noun wider, which would be drift with extra steps.

**Consequences.** No behaviour changes, no signature changes, and no export, type or schema moves: a contract that was already true gains something that owns it. `RA-113` is therefore the red case, because what the source change claims is ownership rather than an answer, and it is measured the way `SH-7` measures the track factory: the rung is declared, both callbacks name it, neither qualifies a child name itself, and the reading ladder it sits on names no `#assertLive`. `RA-112` is green on either side of the change by design, which is what preserving the semantics means. [SESSION-STATUS.md](./SESSION-STATUS.md)'s entry calling the read half open is replaced rather than amended.

**Evidence.** `RA-112` and `RA-113` in `packages/core/test/unit/runtime/handle-base.test.ts`. The red and the green run ids are in the pull request that landed the slice.
