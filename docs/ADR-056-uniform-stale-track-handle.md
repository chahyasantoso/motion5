# ADR-056: A stale TrackHandle refuses uniformly, and `live` is the non-throwing question

**Status:** Accepted, 2026-08-29

**Context.** `ProjectRuntime.#handle` exposed a token-guarded `TrackHandle` with two public failure contracts for one condition. The `track` getter threw `TypeError: Track "<id>" is no longer live.` when its token was stale; `remove()`, `replace()`, `addObserve()` and `removeObserve()` returned silently. A stale mutator reported success by doing nothing; the getter failed loudly. The same comparison was copied into `#removeTrack`, `#replaceTrack`, `#replaceWithObservation` and the getter. `TrackHandle` declared twice, in `runtime/project-runtime.ts` and in `engine.ts`, the defect shape the two private `readNumber` copies had before `plugins/frame.ts` existed.

**Decision.** All-throw. Every handle member routes through one resolver, `#liveEntry(id, token)`, throwing `StaleTrackHandleError` when the captured token is not current. The error extends `TypeError`, keeps the existing message verbatim → a caller narrowing on `instanceof TypeError` or anchored on that string keeps matching; it carries a stable `ruleId` of `stale-track-handle`, what a caller branches on instead. A non-throwing `readonly live: boolean` probe answers the same question for callers whose second call is expected, not mistaken, and `TrackHandle` is declared once, named by both consumers.

Ownership does not move. `ProjectRuntime` holds the tokens and the `TrackEntry` map → stays the only thing answering whether a token is current, the only thing building a handle, the only thing throwing. Nothing enters `Track`, graph code, an adapter or a new lifecycle service. No injection seam: token validation is pure in-memory policy against state this object already holds → a port with exactly one implementation buys a second owner for nothing.

The comparison has one owner, two readers. `#entryIfLive` performs it, `#liveEntry` is that plus the throw, `live` reads the probe → refusal and report cannot disagree about the same handle. `SH-7` pins it as a count: exactly one token comparison in the module, no branch at all inside the handle factory.

**Alternatives rejected.** All-silent would make the getter return `undefined`, giving every caller a nullable to thread through for a condition that is a caller bug. A boolean return from each mutator is the same silence with a value nobody checks. A fifth copied guard beside the four existing was the shape the slice exists to delete.

**Consequences.** Four members now throw where they returned silently. The repository audit in issue #217 reported no caller relying on that silence, wrong by one: `unified-mutation-surface.test.ts` called `remove()` twice across an ABA reuse and asserted the no-op. Migrated to assert the refusal; the guarantee it was really about, that a stale handle never reaches the node that reused its id, unchanged.

A handle survives its own `replace()`. Replacement preserves node identity and therefore the token → a React consumer never sees a node disappear and come back → `live` stays `true` across it. The issue said `live` is `false` after replace; that would invalidate the handle every existing replacement case reuses, so the wording is corrected here, not implemented.

On a disposed project `live` is `false` and never throws, but `remove()` reports the disposal, not the staleness, because `#assertLive()` runs first. The runtime's lifecycle outranks one handle's; `if (handle.live) handle.remove()` is correct either way.

`StaleTrackHandleError` and `TrackHandle` are declared in `contract/track-handle.ts`, not beside the runtime that owns the policy — a gate, not a preference. `public-declaration-surface` refuses any `runtime/` or `graph/` module reachable from the package entry's declaration closure, and a caller cannot `instanceof` an error it cannot name → a public error type cannot live under `runtime/`. The dependency arrow is the one every layer already uses.

**Supersedes in part.** [ADR-026](./ADR-026-track-mutation-capability-handles.md) said `remove` and `replace` are idempotent for stale handles. That is withdrawn. Its token and its ABA guarantee are unchanged; the idempotence is replaced by the refusal plus `live`.

**Evidence.** Cases `SH-1` through `SH-7`. Red run [33249505343](https://github.com/chahyasantoso/motion5/actions/runs/33249505343), archived at `logs/33249505343/` on `ci-logs`: `typecheck` and `format:check` passed first, then `npm test` reported `6 failed | 734 passed`, one failed file out of 155, with integration, boundaries, build, end-to-end and performance all green. `SH-6` passed as a guard by design.

## Amendment, 2026-09-04: the lifecycle outranks the handle on every member that writes, not on the one that asked

The Consequences above state that rule and name one member where it shows: `remove()` reports the disposal, not the staleness, because `#assertLive()` runs first. It ran first there because `#removeTrack` asked it, and asking it was every caller's job. Seventeen of the eighteen writing members this runtime issues across `TrackHandle` and `MotionHandle` never asked; `dispose()` empties the retained maps → the token lookup misses → the resolver answers `StaleTrackHandleError` or `StaleMotionHandleError` instead. One condition, two public failure contracts, decided here, implemented once. Issue #298.

**The invariant.** Every handle member that writes reports `ProjectRuntime is disposed.`, before asking whether the handle is stale.

**A read is unchanged; the asymmetry is the decision, not the amendment's scope.** Staleness on a write misleads specifically: it says the caller's handle is out of date → invites a fresh handle and retry; on a disposed runtime nothing it can do works. Staleness on a read is true — the entry the handle captured is gone — and it is the family this record exists to let a caller catch: changing `definition`, `requires` or `trackIds` would push a bare `Error` past every narrowing on `StaleHandleError` this record asked for. `live` never throws; `if (handle.live) handle.write()` is correct on either side of that line.

**The order has one owner: a rung on the resolver ladder, not a line per caller.** `#writableEntry` and `#writableMotion` ask `#assertLive`, then delegate to `#liveEntry` and `#liveMotion`; `#writableId` delegates to `#writableMotion`. Every writing path resolves through one of the three; every reading member keeps its resolver → probe, reader and writer are three rungs with three readerships, not three copies of one comparison. `#assertLive` named twice in the class, the floor: two retained maps, two refusals, same reason `#liveEntry` and `#liveMotion` were already two members. `SH-7`'s count untouched: none of the three compares a token, none adds a branch to the handle factory.

**Refused: asking `#assertLive` inside `#liveEntry` and `#liveMotion`.** The cheapest change available, one owner and two lines, and it takes the read contract with it silently, for the reason above. `#entryIfLive`, `#motionIfLive` and `#liveOf` refused harder: `live` reads them, and `live` may never throw.

**Refused: a line at the top of each affected path.** Seventeen copies of one ordering; the eighteenth path added later is wrong by default. The defect is one condition with two failure contracts → a fix whose correctness depends on every future author remembering a line is that same defect with a longer fuse. `#removeTrack`'s own `#assertLive()` deleted for the same reason, not left beside the resolver's → `remove()` comes out behaviourally identical, one owner fewer.

**Nothing else in the class moves; measured, not hoped.** `dispose()` clears `#open` → a disposed runtime never has an open recipe → `#assertLive` and `#refuseInsideRecipe` can never both have something to say. Every per-verb order the class documents survives, including ADR-061's amendment's contract for tier 0: liveness joins that sequence at the staleness step, not as a step of its own. The one sequence where both are lexically reachable is a `dispose()` inside a recipe followed by a handle write in the same recipe, and it answers the disposal, the answer ADR-064's amendment of the same date reached for `edit` itself.

**Evidence.** `SH-8` in `stale-track-handle.test.ts`, `RA-111` in `handle-base.test.ts`, one per handle family: two refusals, one file owns each surface. Each adds a writers-and-readers partition of the member record its file already owns, `MEMBER_ARGUMENTS` and `MOTION_MEMBER_ARGUMENTS`, and asserts the partition covers that record's keys exactly → a member added later must be classified, not escape this invariant by omission. Both collect per member, so a red run names every member reporting the wrong condition: `SH-8` red on thirteen of fourteen, `RA-111` on all four. `remove` green in `SH-8` on both sides — this record's own sentence already true of exactly one member. The accepting direction is `SH-1` and `RA-32`, unchanged, green throughout, not restated: a handle made stale on a live runtime still refuses under `StaleHandleError` on every member.

**Consequences.** Seventeen members change which error they throw on a disposed runtime; none changes its signature → no export, type or schema moves. A caller catching `StaleHandleError` around a write to swallow a disposal stops swallowing it, the behaviour this record already called correct for `remove()`. ADR-064's amendment of 2026-09-04 is corrected where it argued two of `#apply`'s callers arrive through handle members answering staleness; they arrive through these resolvers now, and its conclusion holds for six callers, not five. [LIVE-EDIT-COST.md](./LIVE-EDIT-COST.md) gains the caller-facing half, [GUARDRAILS.md](./GUARDRAILS.md) the general rule: a precondition outranking a lookup belongs to the resolver both readers share, not to each caller of it.

## Second amendment, 2026-09-05: a read reports the staleness by decision, and the order it reports it in is a rung

The amendment above states the read half in one paragraph and measures it as an aside. `SH-8` and `RA-111` each assert their file's reading members still answer under `StaleHandleError` after `dispose()`, but inside a case whose subject is the writers, and the status file carried the read as the open question. Issue #300 asked which it is, for the whole `MotionHandle` read surface: `definition`, `trackIds`, `track` and `tryTrack`. It is a decision: this amendment ratifies it, gives it a case of its own, and removes the one thing about it that was never decided at all.

**The invariant.** After `dispose()`, every reading member of a `MotionHandle` refuses with `StaleMotionHandleError` carrying the captured motion id; `tryTrack` refuses rather than answering `undefined`. `id` still answers; `live` still `false`, still never throws. On a live runtime nothing moves: `track()` refuses an unknown child by node id, `tryTrack()` answers `undefined`, a handle made stale while the runtime lives refuses on all four.

**Three refusals are reachable from one lookup; the precedence between them is what this amendment adds.** `handle.track(trackId)` can be wrong three ways at once: the captured Motion gone, the child name ill-formed, the child absent. The order is the Motion, then the name, then the existence → a disposed runtime answers staleness without reading its argument; `qualifyMotionTrack`'s `TypeError` is reachable only on a live handle. Already the behaviour, nobody's decision. It held because an argument is evaluated before the call it is an argument to, and both callbacks nested the resolve inside the qualification inside the delegate → a slice rewriting either would change half this contract with the other half still green.

**`tryTrack` is the member the decision is really about.** The only signature that can absorb a refusal instead of reporting it; `undefined` is not free of meaning there: it already says this child is absent from a live Motion. Answering it for a stale handle collapses two facts a caller branches on differently into one value — the all-silent alternative this record rejected for `TrackHandle`, arriving through a probe, not a mutator. Refused for the same reason, by the same argument.

**The order has one owner: a rung, not an expression per call site.** `#liveChildNode(motionId, token, trackId)` resolves the captured Motion through `#liveId` into a local, qualifies the child, answers a node id; `track` and `tryTrack` are one call each. The shape the amendment above chose for the writes, chosen here for the same reason: one condition, one place answering it, an extension point for the day the answer changes, not two call sites both remembered. The reading ladder is now four rungs with four readerships: `#motionIfLive`, read by `live`, never throws; `#liveMotion`, which a read refuses through; `#liveId`, that plus the id; and this, that plus the child.

**Refused: `#assertLive` inside `#liveMotion` or `#motionIfLive`.** Unchanged from the amendment above; issue #300's own ownership section reaches it independently. `live` reads that ladder, may never throw; a guard there takes this read contract with it silently.

**Refused: a `#readableId` rung beside `#liveId`.** Symmetry with `#writableId` is the argument, and a bad one. `#liveId` already is the read rung; a second name for one member is the duplication this record's original decision exists to delete, spelled as a naming convention.

**Refused: a second member list for the readers.** `MOTION_READERS` already exists in `handle-base.test.ts`; `RA-111` already asserts it and `MOTION_WRITERS` partition `MOTION_MEMBER_ARGUMENTS` exactly. `RA-112` reads that same partition → a member added to `MotionHandle` later still must be classified, not escape this invariant by omission; the two cases cannot drift about which members are reads.

**No standing rule is earned.** [GUARDRAILS.md](./GUARDRAILS.md) already carries the amendment above's rule: a precondition outranking a lookup belongs to the resolver both readers share, not each caller. This slice applies it to an order between two lookups, not restating it one noun wider — drift with extra steps.

**Consequences.** No behaviour, signature, export, type or schema changes: a contract already true gains something that owns it. `RA-113` is therefore the red case — the source change claims ownership, not an answer — measured the way `SH-7` measures the track factory: the rung declared, both callbacks name it, neither qualifies a child name itself, the reading ladder names no `#assertLive`. `RA-112` green on either side by design, which is what preserving the semantics means. [SESSION-STATUS.md](./SESSION-STATUS.md)'s entry calling the read half open is replaced, not amended.

**Evidence.** `RA-112` and `RA-113` in `packages/core/test/unit/runtime/handle-base.test.ts`. The red and green run ids are in the pull request that landed the slice.
