# Taste

- Values avoiding duplication of reusable implementations across apps/demos; prefers shared concerns (e.g., GSAP-backed scroll sources) to live at the core adapter layer rather than being re-implemented in each demo/app. Confidence: 0.7
- Keeps third-party libraries (e.g., gsap) out of core's dependency tree: core defines structural seams (like `GsapLike`) and receives real implementations via dependency injection, while the actual library import/binding lives in the app or test layer. Confidence: 0.8
- Fact-checks claims against the actual source and calls out inaccuracies tersely ("but gsap.ts doesnt import gsap"); expects analysis to be verified against the code rather than assumed. Confidence: 0.7
- Prefers GitHub integration (MCP) authenticated via OAuth — explicitly requests the OAuth flow rather than personal access tokens or other auth. Confidence: 0.6
- Communicates in terse, minimal messages — e.g., a single "404" to report a failed OAuth flow, repeated verbatim when the problem persists, one-sentence task instructions ("github mcp connected. using github mcp file an issue..."), or "vs option B, elaborate" to continue a design discussion — and expects the agent to diagnose the problem / carry on without further prompting. Confidence: 0.9
- Prefers to drive GitHub workflow actions through the GitHub MCP server directly from chat rather than via the browser or manual steps — e.g., filing issues and opening pull requests for branches (a terse "open pr for the branch" is expected to be carried out end-to-end: commit, push, and PR creation). Confidence: 0.8
- When the agent surfaces a code smell, architectural finding, or design decision, prefers it be tracked as a GitHub issue rather than fixed inline in the same session — "create issue for this" after an analysis. Design-decision issues specifically must include the candidate options, their tradeoffs, and a clearly stated preferred option (e.g., "open issue for this with the options and the tradeoffs and preffered option"). Confidence: 0.8
- Considers test doubles (fakes) to belong only in test code, not in demo/app code — a reference demo should wire the real production adapter (e.g., `createGsapInterpolator(gsap)`) rather than a test fake, so demos demonstrate honest production wiring. Confidence: 0.6
- Asks "should it be? or shouldn't?" style and design-critique questions (e.g., "why doesn't it namespaced by the plugin... how to design better keyframes?") and expects an opinionated architectural verdict with concrete design alternatives and a recommendation — not just a description of why the code works; wants the agent to judge whether the current design is right and propose the better one. Also proposes candidate designs of his own and asks "would this work?", expecting feasibility to be checked against the actual contract/compiler before committing. Confidence: 0.8
- Comes from a Dart/Flutter background; asks conceptual questions comparing JS/TS constructs to Dart equivalents (e.g., factory functions vs. factory constructors), so framing explanations with Dart analogies lands well. Confidence: 0.8
- Asks conceptual "why"-style and "what is X used for?" questions to understand the codebase (e.g., why only a `time-driver.ts` exists, what the Scheduler port is for) and expects the agent to read the source and explain the design rationale — purpose, consumption points, and abstraction distinctions — rather than a mere file inventory. Confidence: 0.7
- Follows up on proposed design changes by probing their consequences and edge cases: asks whether adopting an alternative would make an existing mechanism redundant (e.g., "if we use plugin namespace do we need projection at all?") or whether two contract fields will always coincide (e.g., "internal keys will always the same as keys? is there any case they wouldn't be the same"), expecting the agent to verify against the source and decompose each mechanism into its essential/structural role vs. incidental work. Confidence: 0.7
- Prefers related design findings surfaced during an issue discussion to be filed as dependent follow-up issues explicitly linked to (and blocked-by) the parent issue rather than folded into it or filed standalone — e.g., "is this worth an issue for? follow up from issue 165?" for the internalKeys denylist point — so the parent keeps a focused scope and the follow-up is only actionable if the parent's design lands. Confidence: 0.6
- Asks for honest severity classification of flagged design findings — e.g., "as of right now the validator blind spot, is not an issue?" — distinguishing latent/dormant design concerns (only triggered if a future design change lands) from active bugs, and expects the agent to confirm current actuality against the code rather than overstate it as a live problem. Confidence: 0.6
- Wants the full issue thread read start-to-finish — body plus all comments ("read issue 164 comments from start to finish") — before an implementation plan is made, so the plan accounts for the whole discussion and follow-ups, not just the opening description. Confidence: 0.7
- Wants implementation plan work done on a separate branch created from `main` (e.g., `fix/issue-164-...`), never on main itself — "make implementation plan on separate branch" — so the plan/implementation lives on its own reviewable branch. Confidence: 0.7
